    - **DataFrame → RDD lineage translation** — how `QueryExecution` compiles a DataFrame into an `RDD[InternalRow]`: the `Dataset.withAction()` entry point; the four compilation phases (Analyzer → Optimizer → SparkPlanner → PrepareForExecution); how `executedPlan.execute()` walks the `SparkPlan` tree recursively via `executeRDD = LazyTry { doExecute() }`; how each operator's `doExecute()` calls `child.execute()` bottom-up; how `ShuffleExchangeExec` embeds a `ShuffleDependency` into the RDD lineage (via `ShuffledRowRDD.getDependencies`), which is what the DAGScheduler detects as a stage boundary; `QueryExecution.toRdd` as the bridge: `new SQLExecutionRDD(executedPlan.execute(), conf)` (source-verified v4.1.2). The recursive execution tree:
      ```
      root.execute()
        └── root.doExecute()
              └── child.execute()
                    └── child.doExecute()       ← ShuffleExchangeExec: returns ShuffledRowRDD(shuffleDependency)
                          └── leaf.doExecute()  ← FileScanRDD: one partition per input file split
      ```
    - **Bounded-action execution — `executeTake` vs `executeCollect`** (deferred from Chapter 2's Stage 1) — `Dataset.show`/`take`/`head` call `executedPlan.executeTake(n)`, which scans partitions **incrementally**: it runs the first partition, then launches more in widening rounds scaled by `spark.sql.limit.scaleUpFactor` until it has `n` rows, so it usually touches far fewer than all partitions. `collect()` calls `executeCollect()`, which runs **all** partitions. Both decode `InternalRow`s directly and bypass `QueryExecution.toRdd` (only `Dataset.rdd` access takes the `toRdd` path). Source-verified v4.1.2 (`SparkPlan.scala`): `executeCollect` calls `getByteArrayRdd().collect()`; `executeTake` loops `while (buf.length < n && partsScanned < totalParts)`.
    - **Spark 4.x `QueryExecution` phases** (deferred from Chapter 2's Stage 1) — the additional internal phases `commandExecuted`, `tableVersionsRefreshed`, and `normalized` added for SQL scripting and Declarative Pipelines; why standard DataFrame queries pass through them unchanged so the core Analyzer → Optimizer → SparkPlanner → PrepareForExecution pipeline is what matters for DataFrame execution.
    - **Internal row formats** — `InternalRow` (logical row abstraction), `UnsafeRow` (compact binary row used by Tungsten; on-heap by default, off-heap opt-in; reduces GC), and Apache Arrow (columnar format used for cross-process transfer in pandas UDFs); why three formats exist and when each is used
    - **Unmanaged memory tracking** (`UnifiedMemoryManager.scala` L70–91, source-verified v4.1.2) — a third type of memory that `UnifiedMemoryManager` now accounts for, alongside execution memory and storage memory; covers memory consumed by components that manage their own allocations outside the unified pool; two confirmed examples in source: RocksDB state stores (Structured Streaming stateful ops) and native libraries (JNI / off-heap allocations); tracked separately for ON_HEAP and OFF_HEAP modes (`unmanagedOnHeapUsed`, `unmanagedOffHeapUsed`); components register via `registerUnmanagedMemoryConsumer()`; a background daemon thread (`"unmanaged-memory-poller"`) polls registered consumers on a configurable interval (`UNMANAGED_MEMORY_POLLING_INTERVAL`); three stated purposes: visibility into total executor memory, OOM prevention (unmanaged usage is subtracted from available pool before allocation decisions), and debugging; `acquireExecutionMemory` and `acquireStorageMemory` both call `getUnmanagedMemoryUsed()` to reduce the effective pool size before granting memory
    - **Speculative execution detection mechanism** — executor heartbeat protocol, `spark.speculation.quantile = 0.9` (fraction of stage tasks that must complete before speculation begins), `spark.speculation.multiplier = 3` (how many times slower than median before a task is flagged), `spark.speculation.efficiency.enabled = true` (Spark 3.4+)
    - **Determinism requirement behind speculation, retries, and recomputation** — Chapter 2 says speculation is safe because "RDD partitions are immutable"; the precise property is *deterministic recomputation over immutable input* (source file splits and shuffle blocks are write-once), so two attempts over the same input partition produce identical output and a duplicate cannot corrupt results. This is identical for RDD and DataFrame jobs — DataFrames compile to `RDD[InternalRow]`, and speculation is a TaskScheduler-level mechanism agnostic to the job's origin. The real hazard is **non-determinism**, not mutability: `F.rand()`/`F.randn()` without a seed, `F.monotonically_increasing_id()`, non-deterministic UDFs (wall-clock, RNG, network calls), `current_timestamp()`, or reading a source that mutates between attempts. Catalyst tracks `Expression.deterministic` (and operator output ordering) to disable unsafe rewrites; at the scheduler level `RDD.getOutputDeterministicLevel` (`DETERMINATE` / `UNORDERED` / `INDETERMINATE`, SPARK-25341) governs recovery — when an `INDETERMINATE` stage loses output, the DAGScheduler must **re-run the whole stage and all downstream stages** rather than recompute the lost partitions, because a partition-level recompute could disagree with already-completed downstream work. Cover how this interacts with speculation (a speculated `INDETERMINATE` task's output is still accepted because only one attempt's result is committed) and the `ResultStage` rollback limitation (an indeterminate `ResultStage` that has already returned some partitions to the driver cannot be safely re-run — the job fails). This is the mechanism behind Chapter 2's "the two copies cannot interfere," and it answers why the guarantee holds for DataFrame partitions too.
    - **Data locality decision logic** — `spark.locality.wait` (default 3s) and per-level overrides (`spark.locality.wait.process`, `.node`, `.rack`); how the TaskScheduler iterates through locality levels and falls back when no slot at the preferred level is available within the wait window
    - **TaskSet internal representation** — `TaskSet` as an immutable collection; how it interacts with `TaskSetManager`; how the event loop processes task completion events and updates TaskSet state
    - **Shuffle file naming scheme** — how `(shuffleId, mapTaskId, attemptId)` are encoded in shuffle filenames; why attempt-scoped naming ensures retried tasks cannot overwrite successful output; how DAGScheduler uses this to safely resubmit stages
    - **DAGScheduler event loop internals** — `DAGSchedulerEventProcessLoop` class; single daemon thread `"dag-scheduler-event-loop"` draining a `LinkedBlockingDeque`; why most state mutations are single-threaded but some shared structures (notably `cacheLocs`) require explicit `synchronized` guards; source "avoid deadlocks" comment covering ordering of `rdd.stateLock` vs `cacheLocs`; AQE re-planning is not a DAGScheduler event — it runs in `AdaptiveSparkPlanExec`'s own execution context and submits new query stages as normal `JobSubmitted` events; backpressure behaviour when events arrive faster than they can be processed
    - **Cross-job stage sharing — why `JobSubmitted` affects stage state** — the DAGScheduler keeps **one global stage graph shared across all active jobs**, not a private graph per job. When `handleJobSubmitted` walks a new job's lineage, `getOrCreateShuffleMapStage` *reuses* an existing stage for any `ShuffleDependency` already created by a prior or still-running job — adding the new job's id to that stage's `jobIds` set — and treats parent `ShuffleMapStage`s whose `MapStatus` outputs are still registered in `MapOutputTracker` as already available, so the new job's `findMissingPartitions()` depends on state left behind by earlier jobs (this is also how a cached/reused shuffle lets a second job skip recomputation). Because job submission reads and mutates the same shared bookkeeping (`stageIdToStage`, `shuffleIdToMapStage`, `jobIdToStageIds`, `activeJobs`, `MapOutputTracker`) that `CompletionEvent` and `ExecutorLost` also touch, `JobSubmitted` **must** be serialized on the single-threaded event loop alongside them — concurrent handling would race on stage availability (e.g. a completion registering the last `MapStatus` for shuffle X while a new job is deciding whether X's stage is missing) and would otherwise require locks on the hot path. This is the mechanism behind Chapter 2's note that "a new job arriving affects stage state."
    - **Shuffle write/read mechanics** — how map tasks sort and partition output before writing; how reducer-side merge works; why reducers may need to re-sort fetched data if order matters
    - **MapOutputTracker internals** — `MapOutputTrackerMaster` on the driver vs `MapOutputTrackerWorker` on each executor; worker maintains a local `mapStatuses` cache and uses epoch-based invalidation to avoid querying the master on every shuffle read; after every ShuffleMapStage task completes the master registers `shuffleStatuses[shuffleId][mapIndex] → MapStatus (location: BlockManagerId + getSizeForBlock(reduceId): Long)` — key is `mapIndex` (partition index, 0-based), not a task ID; for large shuffle outputs the master delivers statuses via Broadcast rather than direct RPC
    - **MapOutputTracker operational semantics** — whether it is consulted once per stage or once per task; how stale entries are invalidated when an executor dies and its shuffle blocks are re-registered after ShuffleMapStage resubmission
    - **BlockManager internals** — same `BlockManager` class on driver and executors; `isDriver` flag adjusts behaviour (file cleanup, ESS registration); cached partitions and broadcast copies go through `MemoryStore`/`DiskStore`; shuffle data bypasses BlockManager storage: `SortShuffleWriter` writes directly to disk via `shuffleExecutorComponents` / `IndexShuffleBlockResolver`; remote fetch opens a Netty connection via `NettyBlockTransferService`; `NettyBlockRpcServer` handles the request and calls `blockManager.getLocalBlockData(blockId)` → `shuffleManager.shuffleBlockResolver.getBlockData()`; uncached input partitions read directly from HDFS/S3 via `FileScanRDD` / Hadoop `InputFormat`; `BlockId` addressing scheme (`RDDBlockId`, `ShuffleBlockId`, `BroadcastBlockId`); eviction lifetime differences between cached partitions, shuffle files, and broadcast copies
    - **SchedulerBackend RPC internals** — `CoarseGrainedSchedulerBackend` as the shared base for all cluster managers; `DriverEndpoint` as the RPC endpoint executors connect to; `RegisterExecutor` message on startup; `StatusUpdate` message on task completion/failure; `makeOffers()` → `TaskScheduler.resourceOffers(offers)` when a slot becomes free; `launchTasks()` serialising `TaskDescription` and sending to executor; `killTask()` for task-kill signals; `reviveThread` firing `ReviveOffers` periodically so delay scheduling can re-evaluate locality preferences without waiting for a new status update; per-cluster-manager subclasses: `StandaloneSchedulerBackend`, `YarnClientSchedulerBackend` / `YarnClusterSchedulerBackend` (YARN client and cluster deploy modes; `YarnSchedulerBackend` is the abstract base), `KubernetesClusterSchedulerBackend`, `LocalSchedulerBackend` (extends `SchedulerBackend` directly, bypasses `CoarseGrainedSchedulerBackend` entirely)
    - **Executor exclusions (`HealthTracker`)** — when an executor accumulates too many task failures (`MAX_FAILURES_PER_EXEC`), `HealthTracker` marks it excluded and `TaskSchedulerImpl` skips it during slot assignment (`isExecutorExcluded`); exclusion expires after `EXCLUDE_ON_FAILURE_TIMEOUT_MILLIS`; whole nodes can also be excluded via `MAX_FAILED_EXEC_PER_NODE`; `EXCLUDE_ON_FAILURE_KILL_ENABLED` can decommission the executor immediately
    - **Serialization in the shuffle data path** — how `UnsafeRow` binary format avoids extra serialization during shuffle for SQL/DataFrame operations; when Java vs Kryo serialization applies to shuffle data for raw RDD operations

    - **Python worker lifecycle (`pyspark/daemon.py` and `PythonWorkerFactory`)** — daemon.py listens on a socket and forks a new child process **on demand** each time the executor JVM opens a connection (no pre-warmed pool in daemon.py itself); if `SPARK_REUSE_WORKER` is set, the forked child loops on the same socket and handles the next task without exiting (`daemon.py` L232–243: `while True: code = worker(sock, ...); if not reuse or code: break`); the **idle worker pool** is JVM-side (`PythonWorkerFactory.idleWorkers` queue in `PythonWorkerFactory.scala`) — it holds open sockets to alive worker processes between tasks; `releaseWorker()` returns a socket to the pool; the next task dequeues an idle worker rather than asking daemon.py for a new fork; on non-UNIX (Windows), daemon mode is unavailable and workers are spawned directly per connection via `worker.py`
