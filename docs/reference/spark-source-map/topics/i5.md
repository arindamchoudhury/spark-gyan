## What it is

"Partitioning" names three different things that share a word, and most confusion in this topic is the three being conflated:

1. **Read partitioning** — how input files become tasks (`maxPartitionBytes`; see B4).
2. **Shuffle partitioning** — how rows are redistributed across a shuffle boundary. This is what `repartition`, `coalesce`, and `spark.sql.shuffle.partitions` control, and what a `Partitioner` decides.
3. **Storage partitioning** — the `key=value` directory layout `partitionBy` writes (also B4).

Within (2), the distinction that matters is between the two operations people treat as opposites. `repartition` is a **shuffle**; `coalesce` is a **narrow dependency** that merges existing partitions in place. That difference is why `coalesce` is cheaper, and also why it has a failure mode `repartition` does not: reducing partitions without a shuffle reduces the parallelism of *everything upstream in the same stage*.

### The shuffle, and a correctness subtlety

- [exchange/ShuffleExchangeExec.scala:188](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/exchange/ShuffleExchangeExec.scala#L188) — the exchange operator; `prepareShuffleDependency` at L339
- [exchange/ShuffleExchangeExec.scala:347](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/exchange/ShuffleExchangeExec.scala#L347) — round-robin is implemented as a `HashPartitioner` over a synthetic key, not as literal round-robin assignment
- [exchange/ShuffleExchangeExec.scala:424](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/exchange/ShuffleExchangeExec.scala#L424) — the SPARK-23207 comment, worth reading in full: round-robin partitioning **must be deterministic**, because a retried task that assigns rows differently causes *data loss*, not just a reshuffle. Spark guarantees it with a local sort before partitioning (L432), gated by `spark.sql.execution.sortBeforeRepartition` (default `true`). Turning that off trades correctness under retry for speed

### Coalesce — narrow, and therefore contagious

- [basicPhysicalOperators.scala:1233](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/basicPhysicalOperators.scala#L1233) — `CoalesceExec`; its `outputPartitioning` is `SinglePartition` when `n == 1`, otherwise `UnknownPartitioning(n)` — note it does **not** advertise a usable partitioning, so a downstream join or aggregate will shuffle anyway
- [rdd/CoalescedRDD.scala:75](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/CoalescedRDD.scala#L75) — the narrow dependency: child partitions are *grouped*, not redistributed. Since there is no stage boundary, the upstream computation runs with the coalesced task count — so `coalesce(1)` before a write makes the entire preceding stage single-threaded

### AQE — the partition count you asked for is not the one you get

- [adaptive/CoalesceShufflePartitions.scala:34](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/adaptive/CoalesceShufflePartitions.scala#L34) — the AQE rule that merges small post-shuffle partitions
- [adaptive/ShufflePartitionsUtil.scala:44](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/adaptive/ShufflePartitionsUtil.scala#L44) — `coalescePartitions`: targets `advisoryPartitionSizeInBytes`, never producing partitions below `minPartitionSize` (1MB). With AQE on, `spark.sql.shuffle.partitions` is an *upper bound and starting point*, not the final count

## Relevant configs

| Config | Default | Effect |
|---|---|---|
| `spark.sql.shuffle.partitions` | `200` | Post-shuffle partition count; with AQE on this is a starting point that coalescing may reduce |
| `spark.sql.execution.sortBeforeRepartition` | `true` | Local sort before round-robin repartition, guaranteeing determinism under task retry. **Correctness, not performance** |
| `spark.sql.adaptive.coalescePartitions.enabled` | `true` | Merge small post-shuffle partitions at runtime |
| `spark.sql.adaptive.coalescePartitions.initialPartitionNum` | (unset) | Starting count before coalescing; falls back to `shuffle.partitions` |
| `spark.sql.adaptive.coalescePartitions.minPartitionNum` | (unset) | Floor on the coalesced count |
| `spark.sql.adaptive.coalescePartitions.minPartitionSize` | `1MB` | Coalescing never produces partitions smaller than this |
| `spark.sql.adaptive.coalescePartitions.parallelismFirst` | `true` | Prefer keeping parallelism over hitting the advisory size |
| `spark.sql.adaptive.advisoryPartitionSizeInBytes` | (shuffle target) | Target size AQE aims for per partition |
| `spark.sql.adaptive.optimizeSkewsInRebalancePartitions.enabled` | `true` | Split skewed partitions during rebalance |
| `spark.sql.adaptive.rebalancePartitionsSmallPartitionFactor` | `0.2` | Threshold below which a partition is merged during rebalance |
| `spark.default.parallelism` | `max(totalCores, 2)` | RDD-level default; **does not** control DataFrame shuffle partitions |
| `spark.sql.files.maxPartitionBytes` | `128MB` | *Read* partitioning — a different axis entirely (B4) |

## Chapter notes

Gap analysis against **spark-book Ch 16** (`spark-book/ch16-partitioning.md`).

### Already in spark-book ✅

- Physical versus logical partitions
- `repartition(n)` and `coalesce(n)`, and that coalesce avoids a shuffle
- `partitionBy(col)` on writes and the resulting directory layout
- `spark.sql.shuffle.partitions` and its default of 200
- How partition count affects output file count

### Not in spark-book — needs addition ❌

- **`coalesce` reduces the parallelism of the whole upstream stage.** Because `CoalescedRDD` is a narrow dependency there is no stage boundary, so `coalesce(1)` before a write does not merely produce one file — it makes every preceding transformation in that stage run single-threaded. This is the most damaging partitioning mistake in practice, and "coalesce avoids a shuffle" reads as unqualified good news without it. `repartition(1)` is often the correct choice precisely *because* it inserts a shuffle.
- **`repartition` and `coalesce` are one logical node with a boolean.** `Repartition(numPartitions, shuffle, child)` — mirroring the RDD-level `repartition = coalesce(n, shuffle = true)` from I4. Two APIs collapse into one parameter.
- **`coalesce` does not advertise a usable partitioning.** `CoalesceExec.outputPartitioning` is `UnknownPartitioning(n)`, so a downstream join or aggregation shuffles regardless. Coalescing before a keyed operation buys nothing.
- **Round-robin repartition is a correctness problem, solved by a hidden sort.** SPARK-23207: a retried task must assign rows to the same partitions, or rows are *lost* — not merely reshuffled. Spark performs a local sort before round-robin partitioning to guarantee this (`spark.sql.execution.sortBeforeRepartition`, default on). Worth knowing both as a correctness story and because it explains why a bare `repartition(n)` costs more than expected.
- **`repartition(n)` is not literally round-robin.** It is a `HashPartitioner` over a synthetic key. Harmless, but it explains why partition sizes are approximately rather than exactly equal.
- **Partitionings are declarative descriptions, not commands.** Operators advertise `outputPartitioning` and require a distribution; `EnsureRequirements` inserts a shuffle only on mismatch. This is why a manual `repartition(n, "k")` before a `groupBy("k")` is usually redundant — and the same machinery as B7's join exchanges.
- **AQE makes `shuffle.partitions` a starting point, not the answer.** `CoalesceShufflePartitions` merges post-shuffle partitions toward `advisoryPartitionSizeInBytes`, flooring at 1MB. Tuning the static count matters much less than it used to, and the chapter presents it as the primary lever.
- **`RebalancePartitions` is the modern answer to output sizing.** Instead of guessing a count, ask AQE to size partitions at runtime. Directly addresses the "10,000 tiny files" problem the topic exists to solve.
- **`RangePartitioner` samples the data first.** Constructing one runs a job before the real job — the cost of `repartitionByRange` and of any global sort.
- **`spark.default.parallelism` does not control DataFrame shuffles.** It is the RDD-level default; DataFrame shuffles use `spark.sql.shuffle.partitions`. A common misconfiguration, and the two are easy to conflate since I4 covers the former.
