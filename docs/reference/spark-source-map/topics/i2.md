## What it is

A window function computes a value per row using a *set* of neighbouring rows, without collapsing them the way `groupBy` does. Three parts define that set: the **partition** (`partitionBy`), the **ordering** (`orderBy`), and the **frame** — which rows relative to the current one are in scope.

The frame is where nearly all the surprises live, because you usually do not write one. Spark fills in a default, and **that default depends on whether you supplied an ordering** — with different frame *types*, not just different bounds. Physically, `WindowExec` requires its input already partitioned and sorted, so every window is a shuffle plus a sort; and if you omit `partitionBy`, the required distribution becomes `AllTuples`, meaning the entire dataset lands in one partition on one executor.

### The spec and the frame types

- [windowExpressions.scala:47](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/windowExpressions.scala#L47) — `WindowSpecDefinition(partitionSpec, orderSpec, frameSpecification)`: the three parts, together
- [windowExpressions.scala:141](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/windowExpressions.scala#L141) — `RowFrame` versus `RangeFrame` (L157). `ROWS` counts *physical rows*; `RANGE` compares *values* against the ordering column, so all rows tied on that value are peers and enter the frame together. Two rows with the same timestamp are one row apart under `ROWS` and zero apart under `RANGE`
- [windowExpressions.scala:199](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/windowExpressions.scala#L199) — `SpecifiedWindowFrame`; `UnspecifiedFrame` (L193) is the placeholder before resolution
- [windowExpressions.scala:346](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/windowExpressions.scala#L346) — `WindowExpression(windowFunction, windowSpec)`

### The default frame — read this once and the behaviour stops being mysterious

- [analysis/WindowResolution.scala:61](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/analysis/WindowResolution.scala#L61) — `resolveFrame`, and the decision is explicit in the source:
  - a function with a required frame (`row_number`, `rank`, `lead`/`lag`) imposes its own, and a conflicting explicit frame **raises** (L68–L70)
  - **`orderBy` present** → `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` (L78)
  - **no `orderBy`** → `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` (L80)

  So adding an `orderBy` to an aggregate window silently converts it from a whole-partition aggregate into a *running* one — and the frame type changes from `ROWS` to `RANGE` at the same time
- [Analyzer.scala:3449](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/analysis/Analyzer.scala#L3449) — `ExtractWindowExpressions`: lifts window expressions out of the `Project` into a dedicated `Window` node. Rule ordering at L576–L577

### Physical requirements — every window is a shuffle and a sort

- [window/WindowExecBase.scala:35](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/window/WindowExecBase.scala#L35) — `requiredChildDistribution`. ### Frame implementations — the cost model

- [window/WindowFunctionFrame.scala:39](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/window/WindowFunctionFrame.scala#L39) — the abstraction; one concrete class per frame shape, and which you get determines the work per row:
  - `UnboundedWindowFunctionFrame` (L517) — whole partition, aggregate computed **once**
  - `UnboundedPrecedingWindowFunctionFrame` (L565) — running total, updated incrementally
  - `SlidingWindowFunctionFrame` (L422) — bounded both ends; rows enter and leave, so it is the expensive shape
  - `FrameLessOffsetWindowFunctionFrame` (L236) — `lag`/`lead`; no buffering at all, which is why offsets are cheap
- [window/SegmentTreeWindowFunctionFrame.scala](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/window/SegmentTreeWindowFunctionFrame.scala) — a segment-tree strategy for sliding frames, **opt-in** via `spark.sql.window.segmentTree.enabled` (default `false`) and only above `minPartitionRows`. Worth knowing when a wide sliding window is the bottleneck

### Top-N per group — the optimization that changes the algorithm

- [optimizer/InferWindowGroupLimit.scala:54](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/optimizer/InferWindowGroupLimit.scala#L54) — recognises a filter on `row_number`/`rank`/`dense_rank` ≤ *n* and inserts a `WindowGroupLimit` ([basicLogicalOperators.scala:1305](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/plans/logical/basicLogicalOperators.scala#L1305)) that drops non-qualifying rows **before** the shuffle. This is why the idiomatic "rank then filter" top-N pattern is efficient rather than wasteful — but only when the filter is a recognisable form and *n* is under `spark.sql.optimizer.windowGroupLimitThreshold` (1000)

## Chapter notes

Gap analysis against **spark-book Ch 14** (`spark-book/ch14-window-functions.md`).

### Already in spark-book ✅

- `Window.partitionBy().orderBy()` and the window-spec builder
- Ranking functions (`rank`, `dense_rank`, `percent_rank`, `ntile`, `row_number`)
- Analytic functions (`lag`, `lead`, `cume_dist`)
- Frame boundaries via `rowsBetween` / `rangeBetween`
- Windows as a one-pass alternative to a self-join

### Not in spark-book — needs addition ❌

- **The default frame changes when you add `orderBy` — including its type.** With no ordering: `ROWS UNBOUNDED PRECEDING TO UNBOUNDED FOLLOWING` (whole partition). With an ordering: `RANGE UNBOUNDED PRECEDING TO CURRENT ROW` (running). So `F.sum("x").over(Window.partitionBy("k"))` and the same window with `.orderBy("t")` compute *different things*, and neither is written down in the user's code. This is the single most consequential fact in the topic and it is decided in six lines of `WindowResolution.resolveFrame`.
- **`RANGE` and `ROWS` differ on ties, and `RANGE` is the default with ordering.** `ROWS` counts physical rows; `RANGE` compares ordering *values*, so all peers tied on that value enter the frame together. A running sum over a timestamp with duplicates gives different answers under each — and the default is `RANGE`.
- **Omitting `partitionBy` sends the whole dataset to one partition.** `requiredChildDistribution` returns `AllTuples`, and Spark logs "No Partition Defined for Window operation!". It works on sample data and does not scale, with only a log line as warning. The chapter should say this outright.
- **Every window is a shuffle plus a sort.** `requiredChildDistribution` and `requiredChildOrdering` are hard requirements, so `EnsureRequirements` inserts both. That is the cost model, and it explains why chaining several differently-partitioned windows is expensive.
- **Which frame implementation runs determines the per-row work.** Unbounded frames compute once per partition; unbounded-preceding frames update incrementally; sliding frames add and remove rows continuously; `lag`/`lead` buffer nothing. "Narrow your frame" becomes actionable once these are named.
- **Top-N per group is optimized — but conditionally.** `InferWindowGroupLimit` pushes a `row_number() <= n` filter below the shuffle as a `WindowGroupLimit`, which is why rank-then-filter is the idiomatic top-N. It only fires for recognised comparison forms and *n* ≤ `windowGroupLimitThreshold` (1000), so a large *n* or an unusual predicate silently reverts to ranking everything.
- **Window buffers spill, with their own thresholds.** `spark.sql.windowExec.buffer.*` govern it independently of the aggregate spill settings in B6 — relevant whenever a single partition holds many rows.
- **A function with a required frame rejects a conflicting explicit frame.** `row_number`, `rank` and the offset functions impose their own frame; supplying an incompatible `rowsBetween` raises at analysis rather than being ignored.
- **Segment-tree evaluation exists for sliding frames.** New in 4.x and off by default; worth knowing before concluding a wide sliding window is inherently slow.
