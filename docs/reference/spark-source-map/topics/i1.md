## What it is

Arrays, maps and structs are ordinary column values with a nested physical layout — `UnsafeArrayData` and `UnsafeMapData` sit inside the same `UnsafeRow` as everything else. What makes them a distinct topic is that three different *shapes* of operation apply to them, and choosing the wrong one is where the cost is:

- **Extractors** (`struct.field`, `arr[0]`, `map[k]`) are plain expressions — one row in, one row out.
- **Generators** (`explode`, `posexplode`, `inline`) are not expressions at all. They live in a separate `Generate` plan node because they change the *number of rows*.
- **Higher-order functions** (`transform`, `filter`, `aggregate`) take a lambda and stay within one row, so they replace an explode-then-regroup round trip entirely.

The most common mistake in this topic is reaching for a generator when a higher-order function would do — an explode/`groupBy` pair shuffles, while `transform` does not.

## Code path

```
--- extractors: one row in, one row out ---

df.select("s.field")   → GetStructField     [complexTypeExtractors.scala:209]
df.select(F.col("a")[0]) → GetArrayItem     [complexTypeExtractors.scala:355]
                             failOnError = ansiEnabled [:358]
df.select(F.col("m")["k"]) → GetMapValue    [complexTypeExtractors.scala:786]

--- generators: row count changes, so a separate plan node ---

df.select(F.explode("arr"))
  → Explode                                 [generators.scala:422]   (ExplodeBase [:336])
  → logical Generate                        [basicLogicalOperators.scala:291]
  → GenerateExec                            [execution/GenerateExec.scala:59]

F.explode_outer(...)  [functions.scala:9262]
  → GeneratorOuter wrapper                  [generators.scala:318]
      emits one null row instead of zero for a null/empty array
F.posexplode [:507]   adds the index;  F.inline [:586] expands array<struct> to columns

--- higher-order functions: lambda, no row-count change, no shuffle ---

F.transform("arr", lambda x: x + 1)
  → ArrayTransform                          [higherOrderFunctions.scala:312]
  → LambdaFunction                          [higherOrderFunctions.scala:113]
  → ResolveLambdaVariables                  [analysis/higherOrderFunctions.scala:37]
     binds the lambda's variables during analysis
  siblings: ArrayFilter [:581], ArrayAggregate [:814]

--- building maps ---

F.create_map / map_from_arrays
  → ArrayBasedMapBuilder                    [util/ArrayBasedMapBuilder.scala:62]
      duplicate key → EXCEPTION (default) or LAST_WIN [:87-:89]

--- collecting back into a collection ---

F.collect_list / F.collect_set             [aggregate/collect.scala:118 / :196]
  → Collect[T] extends TypedImperativeAggregate [aggregate/collect.scala:48]
      non-mutable buffer → ObjectHashAggregateExec (see B6)

--- the optimizer reads only the fields you touch ---

NestedColumnAliasing                        [optimizer/NestedColumnAliasing.scala:85]
     + spark.sql.optimizer.nestedSchemaPruning.enabled
```

### Extractors

- [complexTypeExtractors.scala:209](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/complexTypeExtractors.scala#L209) — `GetStructField(child, ordinal, name)`: struct access resolves to an **ordinal** at analysis time. - [complexTypeExtractors.scala:786](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/complexTypeExtractors.scala#L786) — `GetMapValue`: a missing key yields null rather than raising, so map lookup and array indexing behave differently under ANSI

### Generators — the operations that change row count

- [generators.scala:336](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/generators.scala#L336) — `ExplodeBase`, the shared parent of `Explode` (L422) and `PosExplode` (L507)
- [generators.scala:318](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/generators.scala#L318) — `GeneratorOuter`: the wrapper that makes `explode_outer` differ from `explode`. A generator cannot appear in an arbitrary expression position precisely because it needs this node — the reason `explode` inside a `withColumn` behaves unlike other functions
- [execution/GenerateExec.scala:59](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/GenerateExec.scala#L59) — the physical operator

### Higher-order functions — the alternative to exploding

### Map construction

- [util/ArrayBasedMapBuilder.scala:62](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/util/ArrayBasedMapBuilder.scala#L62) — reads `spark.sql.mapKeyDedupPolicy`; a duplicate key **raises** by default (L87), or keeps the last value under `LAST_WIN` (L89). Building a map from data with repeated keys fails the job unless you opt into the other policy

### Collecting back

- [aggregate/collect.scala:48](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/aggregate/collect.scala#L48) — `Collect[T] extends TypedImperativeAggregate`: the buffer is a growable JVM collection, **not** a mutable fixed-width buffer. That is exactly the condition from B6 that forces `ObjectHashAggregateExec`, whose sort-based fallback triggers after 128 groups
- [aggregate/collect.scala:118](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/aggregate/collect.scala#L118) — `CollectList`; `CollectSet` (L196) with `ignoreNulls = true` by default and a `mutable.HashSet` buffer — so **neither preserves order**, and `collect_set` silently drops nulls

### Physical layout and pruning

- [UnsafeArrayData.java:69](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/java/org/apache/spark/sql/catalyst/expressions/UnsafeArrayData.java#L69) and [UnsafeMapData.java:47](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/java/org/apache/spark/sql/catalyst/expressions/UnsafeMapData.java#L47) — complex values live in the same off-heap-capable binary format as flat rows; a `UnsafeMapData` is literally two `UnsafeArrayData`s (keys and values)
- [optimizer/NestedColumnAliasing.scala:85](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/optimizer/NestedColumnAliasing.scala#L85) — nested schema pruning: selecting `s.a` from a wide struct reads only that field from Parquet/ORC. ## Chapter notes

Gap analysis against **spark-book Ch 13** (`spark-book/ch13-complex-types.md`).

### Already in spark-book ✅

- `ArrayType`, `MapType`, `StructType` as column values
- `explode`, `posexplode`, `explode_outer`
- Array functions (`array_contains`, `size`, `array_distinct`)
- Struct dot notation and field access
- `collect_list` / `collect_set`

### Not in spark-book — needs addition ❌

- **`explode` silently drops rows; `explode_outer` does not.** A null or empty array produces **zero** output rows, so the parent row vanishes. This is data loss that looks like correct behaviour, and the `GeneratorOuter` wrapper is the whole difference between the two functions. It deserves to be stated as a data-correctness rule, not as a variant listed alongside the others.
- **Higher-order functions replace explode/re-group entirely.** `transform`, `filter` and `aggregate` operate within a row, so no shuffle occurs — whereas `explode` + `groupBy` shuffles the expanded data. Same result, categorically different cost. The chapter lists the functions; it does not present them as the alternative to the generator pattern.
- **Lambdas are Catalyst expressions, not Python callables.** `LambdaFunction` compiles and runs in the JVM, so a higher-order function costs nothing at the Python boundary — unlike a UDF doing the same work. That is the argument for preferring them, and it connects directly to I3.
- **Generators need their own plan node, which is why they behave oddly in `withColumn`.** `Generate` exists because a generator changes the row count; a generator cannot sit in an arbitrary expression position. This explains the errors people hit putting `explode` in the wrong place.
- **Duplicate map keys raise by default.** `spark.sql.mapKeyDedupPolicy` is `EXCEPTION`, so building a map from data with repeated keys fails the job. `LAST_WIN` is opt-in. A common surprise when converting real data to maps.
- **Array index out of range raises under ANSI, but a missing map key returns null.** Two container types, two behaviours, both correct — worth stating side by side since ANSI is now the default (see B3).
- **`collect_set` drops nulls and neither collect preserves order.** `ignoreNulls = true` by default, and the buffers are a `mutable.HashSet` / growable list — so ordering is not guaranteed. Code relying on collected order is relying on an accident.
- **`collect_list`/`collect_set` force `ObjectHashAggregateExec`.** Their buffer is a growable JVM collection, which is precisely the non-mutable case from B6 — so adding one of them to an aggregate changes the operator and brings a 128-group sort fallback with it.
- **Nested schema pruning reads only the fields you reference.** Selecting `s.a` from a wide struct reads just that field from Parquet/ORC. Struct access is therefore cheap in a way that is worth teaching, since it removes the temptation to flatten defensively.
- **`inline` does in one step what explode-plus-extraction does in two.** For the very common `array<struct>` shape it is the more direct tool and is absent from the chapter.
