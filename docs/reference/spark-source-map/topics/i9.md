## What it is

**The medallion architecture has no source code.** Bronze / Silver / Gold is a naming convention for a layered pipeline, not a Spark or Delta construct — there is no `MedallionTable`, no config, nothing to trace. Any trace claiming otherwise would be inventing one.

What *is* traceable is the set of mechanisms the pattern is assembled from, and this is the useful framing for the topic: medallion is a discipline about **where you spend correctness effort**, implemented with four concrete features that each have real semantics worth knowing.

| Layer transition | Mechanism | What it actually does |
|---|---|---|
| source → bronze | streaming/incremental read + append | offset tracking so each file is processed once |
| bronze → silver | schema enforcement, `MERGE INTO` | rejects or evolves schema; rewrites touched files |
| silver → gold | aggregation (B6), `MERGE` for SCD | ordinary Spark work |
| any layer, downstream | Change Data Feed | read row-level changes instead of rescanning |

The pattern's value is that each transition has a *different* failure mode, and the layers exist so that a failure at one is recoverable from the layer above.

## Key source locations

Delta anchors verified against `delta-io/delta` `v4.3.1` on 2026-07-18.

### Incremental ingest — what makes bronze restartable

- [sources/DeltaSource.scala:696](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/sources/DeltaSource.scala#L696) — the streaming source; `latestOffset` (L923, L931, L243) and `getBatch` (L1069)
- [sources/DeltaSourceOffset.scala:55](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/sources/DeltaSourceOffset.scala#L55) — the offset is `(reservoirVersion, index)`: a table **version plus a position within that version's `AddFile` sequence** (documented at L43–L45). That second component is why a single enormous commit can be consumed across several micro-batches rather than in one — the mechanism behind `maxFilesPerTrigger` actually working, and the reason a bronze stream can be restarted mid-commit without reprocessing

### Schema enforcement — the silver layer's actual job

- [schema/ImplicitMetadataOperation.scala:69](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/schema/ImplicitMetadataOperation.scala#L69) — `updateMetadata`: every Delta write passes through here, so schema checking is not opt-in
- [schema/ImplicitMetadataOperation.scala:213](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/schema/ImplicitMetadataOperation.scala#L213) — `mergeSchema`, delegating to [SchemaMergingUtils.mergeSchemas](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/schema/SchemaMergingUtils.scala#L153). Whether an unexpected column **evolves the table or fails the write** is decided here, by the `mergeSchema` option or `autoMerge` config (L87, L140)
- [schema/SchemaUtils.scala:521](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/schema/SchemaUtils.scala#L521) — `isReadCompatible`, and `canChangeDataType` (L1116): the rules for which schema changes are legal. Adding a nullable column is; narrowing a type is not. This is what "schema enforcement at each layer" concretely means

### `MERGE INTO` — two jobs, not one

- [commands/MergeIntoCommand.scala:63](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/commands/MergeIntoCommand.scala#L63) — the command; `runMerge` at L85
- [commands/MergeIntoCommand.scala:133](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/commands/MergeIntoCommand.scala#L133) — `findTouchedFiles`: **a full join between source and target** to determine which data files contain matching rows
- [commands/MergeIntoCommand.scala:138](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/commands/MergeIntoCommand.scala#L138) — `writeAllChanges` (also L155): rewrites each touched file in full

  So a `MERGE` is **two passes over the data plus a full file rewrite**, and its cost is driven by how many files the matches are spread across rather than by how many rows change. Updating 10 rows scattered across 500 files rewrites 500 files. This is the single most important performance fact about the silver layer, and it is why partitioning and clustering choices matter so much here — an insert-only merge skips the rewrite path entirely

### Change Data Feed — the alternative to rescanning

- [commands/cdc/CDCReader.scala:59](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/commands/cdc/CDCReader.scala#L59) — reads row-level changes between versions; `_change_type` at L64, the full injected column set at L102. Lets a gold layer consume *what changed* rather than recomputing from a silver snapshot

## Relevant configs

| Config | Default | Effect |
|---|---|---|
| `spark.databricks.delta.schema.autoMerge.enabled` | `false` | Whether a write with new columns evolves the schema or fails. **The silver layer's central policy decision** |
| `spark.databricks.delta.merge.repartitionBeforeWrite.enabled` | `true` | Repartition before writing merge output, reducing small files |
| `delta.enableChangeDataFeed` (table property) | `false` | Must be on *before* the changes you later want to read |
| `spark.databricks.delta.streaming.schemaTrackingLocation` | (unset) | Tracks schema changes for a stream reading an evolving table |
| `maxFilesPerTrigger` / `maxBytesPerTrigger` (read option) | (unset) | Bounds micro-batch size — effective because offsets carry an index within a version |
| `spark.sql.shuffle.partitions` | `200` | Governs the merge's join and the aggregation in gold (B6, B7) |

## Chapter notes

**Chapter 20 is not yet written — this trace is drafting material.** The topic is a *pattern*, so the chapter's value depends on connecting the convention to real mechanisms rather than restating the three-layer diagram.

### Points the chapter should not miss ❗

- **Say plainly that medallion is a convention, not a feature.** There is no code, no config, no API. Bronze/Silver/Gold names a discipline about where correctness effort goes. A chapter that presents it as a Spark or Delta capability misleads; one that presents it as a naming scheme *plus four mechanisms* is useful.
- **`MERGE` is two jobs and a file rewrite.** `findTouchedFiles` joins source against target to locate matches, then `writeAllChanges` rewrites each touched file in full. Cost scales with **how many files the matches are spread across**, not how many rows change — updating 10 scattered rows can rewrite 500 files. Everything about silver-layer layout follows from this, and it makes "partition thoughtfully" an argument rather than an instruction.
- **Schema enforcement is a per-write decision with explicit rules.** Every write goes through `updateMetadata`; whether a new column evolves the table or fails is `autoMerge`/`mergeSchema`, and which changes are legal at all is `isReadCompatible`/`canChangeDataType`. "Enforce schema at silver" means choosing this policy deliberately per layer — permissive at bronze, strict at silver is the usual shape.
- **Stream offsets carry a position *within* a version.** `DeltaSourceOffset` is `(reservoirVersion, index)`, which is why `maxFilesPerTrigger` works and why a restart mid-commit does not reprocess the whole commit. Without this, "incremental processing" is hand-waving.
- **CDF must be enabled before the changes you want to read.** `delta.enableChangeDataFeed` is not retroactive — the same trap as event logging in I7, and worth stating because the gold layer is exactly where someone reaches for it after the fact.
- **The layers exist so failures are recoverable.** Bronze keeps raw data so silver can be rebuilt; silver keeps cleaned history so gold can be recomputed. That is the actual justification for the storage cost, and it is the part a diagram does not convey.
- **Delta's Spark-version constraint applies here too.** This topic depends entirely on Delta, which does not build against Spark 4.2.0 (see I8).
