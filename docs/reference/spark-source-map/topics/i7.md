## What it is

The Spark UI is not an instrumentation layer wired into the engine. It is a **read model built from an event stream**: the scheduler emits `SparkListenerEvent`s, those events go onto an asynchronous queue, listeners consume them and write into a key-value store, and the UI pages render that store.

Two consequences follow, and both matter more than any individual tab. First, the UI is *derived* — if events are dropped, the UI is quietly wrong, and it is designed to drop events rather than slow the job down. Second, the same event stream can be written to disk (`spark.eventLog.enabled`), which is exactly what the History Server replays; the live UI and the History Server are the same read model over the same data, differing only in whether the events arrive live or from a file.

## Key source locations

### The pipeline — and where it silently loses data

- [scheduler/AsyncEventQueue.scala:38](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/AsyncEventQueue.scala#L38) — events are delivered **asynchronously** through a bounded queue, so a slow listener cannot block the scheduler
- [scheduler/AsyncEventQueue.scala:164](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/AsyncEventQueue.scala#L164) — `eventQueue.offer(event)`; on failure the event is **dropped** (L170) and an error is logged exactly once (L173): *"This likely means one of the listeners is too slow and cannot keep up with the rate at which tasks are being started by the scheduler."*

  This is the single most important fact about the UI as a diagnostic tool: **under heavy load the UI is incomplete by design**. Missing tasks, wrong totals, and stages that never appear finished are all explained by this, and the only signal is one log line plus a counter. Capacity is `spark.scheduler.listenerbus.eventqueue.capacity` (10000)
- [status/AppStatusListener.scala:46](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/status/AppStatusListener.scala#L46) — turns the event stream into entities
- [status/AppStatusStore.scala:42](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/status/AppStatusStore.scala#L42) — the KV store every page queries. The UI never asks the scheduler anything

### The tabs

- [ui/SparkUI.scala:98](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/ui/SparkUI.scala#L98) — `initialize()` attaches the tabs in order: Jobs (L100), Stages (L102), Storage (L103), Environment (L104), Executors (L112), and a driver-log tab when configured (L107). The SQL tab is separate and attached only when SQL is used
- [sql/.../ui/SQLTab.scala:24](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/ui/SQLTab.scala#L24) — the SQL tab, backed by [SQLAppStatusStore.scala:37](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/ui/SQLAppStatusStore.scala#L37) and fed by [SQLAppStatusListener.scala:41](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/ui/SQLAppStatusListener.scala#L41). Entries appear only for executions registered via `SQLExecution.withNewExecutionId` — which is why a transformation with no action leaves no trace here (see B3)
- [sql/.../ui/SparkPlanGraph.scala:35](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/ui/SparkPlanGraph.scala#L35) — the plan diagram; `SparkPlanGraphNode` (L218) carries the per-operator metrics. The plan shown here is the **post-AQE** plan, which is why it can differ from `df.explain()` output (B3, B7)

### The same events, on disk

- [scheduler/EventLoggingListener.scala:48](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/EventLoggingListener.scala#L48) — writes the event stream as JSON when `spark.eventLog.enabled`. The History Server replays that file through the same listeners, so **it can only show what was logged**: turning event logging on *after* the interesting run is too late, and events dropped from the live bus are equally absent from the log

### Programmatic access

- [status/api/v1/ApiRootResource.scala:43](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/status/api/v1/ApiRootResource.scala#L43) — the REST API at `/api/v1`, `/applications` at L46. Everything the UI renders is available as JSON, from both the live UI and the History Server — the route to automated regression checks rather than eyeballing pages

## Relevant configs

| Config | Default | Effect |
|---|---|---|
| `spark.ui.enabled` | `true` | Serve the UI at all |
| `spark.ui.port` | `4040` | Increments if taken — a second app on one host lands on 4041 |
| `spark.ui.retainedJobs` | `1000` | Jobs kept in the store; older ones disappear from the UI |
| `spark.ui.retainedStages` | `1000` | Same for stages |
| `spark.ui.retainedTasks` | `100000` | Same for tasks — reached quickly by a wide job |
| `spark.sql.ui.retainedExecutions` | `1000` | SQL-tab entries retained |
| `spark.scheduler.listenerbus.eventqueue.capacity` | `10000` | Queue depth before events are **dropped**; raise when the UI looks incomplete under load |
| `spark.eventLog.enabled` | `false` | **Off by default** — no History Server data unless set before the run |
| `spark.eventLog.dir` | (default log dir) | Where event logs are written |
| `spark.eventLog.rolling.enabled` | `true` | Roll event logs, capped by `rolling.maxFileSize` (128m) |
| `spark.eventLog.compress` | `true` | Compress event logs (ZSTD) |
| `spark.eventLog.logStageExecutorMetrics` | `false` | Per-stage executor memory metrics — off by default, and needed for memory forensics after the fact |
| `spark.ui.prometheus.enabled` | `true` | Prometheus-format metrics endpoint |
| `spark.ui.threadDumpsEnabled` | `true` | Live executor thread dumps — the tool for a hung task |
| `spark.ui.reverseProxy` | `false` | Serve the UI behind a proxy (common on managed clusters) |
| `spark.executor.metrics.pollingInterval` | `0` (heartbeat only) | More frequent executor metric sampling |

## Chapter notes

**Chapter 18 is not yet written — this trace is source material for drafting it.** The learning-path topic scopes it as: jobs/stages/tasks, the SQL tab and plan phases, DAG visualisation, shuffle read/write metrics, and spill indicators.

### Points the chapter should not miss ❗

- **The UI is a read model over a lossy event stream.** Nothing in it is measured directly; everything is derived from `SparkListenerEvent`s consumed asynchronously. Leading with this makes every later oddity explicable instead of mysterious.
- **Events are dropped under load, by design.** A full queue discards events so the scheduler is never blocked, with one log line and a counter as the only evidence. A chapter that teaches the UI as ground truth is teaching something false — and `spark.scheduler.listenerbus.eventqueue.capacity` is the fix when totals look wrong on a busy job.
- **Retention limits mean old data simply vanishes.** `retainedJobs`/`retainedStages` (1000) and `retainedTasks` (100000) are reached quickly by a wide job, so a long-running application loses its early history from the live UI.
- **The SQL tab shows the post-AQE plan.** `df.explain()` prints the plan *before* AQE re-decides, so the two legitimately disagree — the same finding as B3 and B7, and the SQL tab is where you see what actually ran.
- **No action means no SQL-tab entry.** Executions register through `SQLExecution.withNewExecutionId`, so a chain of transformations produces nothing to look at (B3).
- **Event logging is off by default, and cannot be applied retroactively.** The History Server can only replay what was logged; enabling it after an incident is too late. `logStageExecutorMetrics` is additionally off, and it is what you need for memory forensics.
- **Everything is available as JSON at `/api/v1`.** Worth teaching alongside the pages, because it turns "check the UI" into something automatable — regression checks on stage durations or shuffle volumes.
- **Thread dumps are the tool for a hung task.** A stage stuck at one task is diagnosed by the executor thread dump, not by staring at the timeline.
- **Port 4040 increments per application on a host.** Trivial, universally hit, and worth one sentence.
- **The UI was rebuilt in 4.2.0** ([SPARK-55760]) with dark mode and searchable, zoomable, side-by-side SQL plan visualisation — so book screenshots (Rioux Ch 11, LS2e Ch 7) no longer match. The tabs and their meanings are unchanged; the layout is not.
