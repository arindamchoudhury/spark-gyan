## What it is

Null in Spark is SQL's three-valued logic, implemented in two places that are easy to conflate. At the **storage** level a null is a bit in `UnsafeRow`'s null bitmap — the value slot still exists, so nullity is a property of the row, not a sentinel value. At the **expression** level every `Expression` declares `nullable`, and comparisons involving null evaluate to null rather than to false.

That second point is the whole topic. `NULL = NULL` is not true, it is *unknown*; a `WHERE` clause keeps only rows where the predicate is literally `true`, so unknown is discarded exactly like false — but the two behave differently everywhere else. Aggregates skip nulls, `GROUP BY` groups them together, joins never match them, and `count` treats them differently depending on what you pass it. None of these are special cases; they are all consequences of the same rule applied in different contexts.

## Key source locations

All anchors verified against the `v4.2.0` tag on 2026-07-18.

### How a null is stored

- [UnsafeRow.java:115](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/java/org/apache/spark/sql/catalyst/expressions/UnsafeRow.java#L115) — `bitSetWidthInBytes`: every `UnsafeRow` begins with a null bitmap, sized at construction (L138). `setNullAt` (L198) sets the bit and leaves the value slot in place. Null is therefore not a magic value in the data — it is metadata alongside it, which is why nullity survives any type

### Nullability as a declared property

- [Expression.scala:134](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/Expression.scala#L134) — `def nullable: Boolean` on every expression. The optimizer trusts it to omit null checks, which is the mechanism behind B5's finding that a false `nullable = false` produces wrong results rather than errors

### Three-valued logic

- [predicates.scala:1108](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/predicates.scala#L1108) — `EqualTo`: null on either side yields null, never false
- [predicates.scala:1156](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/predicates.scala#L1156) — `EqualNullSafe` (`<=>`, `eqNullSafe`): treats null as a comparable value, so `null <=> null` is true. The only way to join or compare on keys that may be null
- [nullExpressions.scala:425](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/nullExpressions.scala#L425) — `IsNull`; `IsNotNull` (L459). These are the *only* correct null tests — `col == None` in Python builds an `EqualTo` against a null literal, which is always null and therefore never matches

### The null-function family

- [nullExpressions.scala:52](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/nullExpressions.scala#L52) — `Coalesce`: first non-null of N
- [nullExpressions.scala:173](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/nullExpressions.scala#L173) — `NullIf`: inverse — produce null when two values are equal. `NullIfZero` (L206), `Nvl` (L246) and `Nvl2` (L271) are further SQL-compatibility aliases in the same file
- [nullExpressions.scala:346](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/nullExpressions.scala#L346) — `NaNvl`: **`NaN` is not null**. A float column can carry both, and only this function handles `NaN` — `coalesce` will happily return a `NaN`

### Optimizer rules that rewrite nulls away

- [optimizer/expressions.scala:900](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/optimizer/expressions.scala#L900) — `NullPropagation`: folds provably-null expressions into a null literal before execution
- [optimizer/ReplaceNullWithFalseInPredicate.scala:53](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/optimizer/ReplaceNullWithFalseInPredicate.scala#L53) — the rule that makes "null behaves like false in a WHERE" concrete: inside a filter or join condition the two are interchangeable, so Spark substitutes `false` to enable further simplification. Outside a predicate they are emphatically not interchangeable

### `dropna` / `fillna`

- [api/DataFrameNaFunctions.scala:49](https://github.com/apache/spark/blob/v4.2.0/sql/api/src/main/scala/org/apache/spark/sql/DataFrameNaFunctions.scala#L49) — `drop(how)`; the mapping at [L114](https://github.com/apache/spark/blob/v4.2.0/sql/api/src/main/scala/org/apache/spark/sql/DataFrameNaFunctions.scala#L114) is worth reading once: **`"any"` → `None`, `"all"` → `Some(1)`**. Both `how` values and `thresh` are the same parameter underneath — a minimum count of non-null columns
- [classic/DataFrameNaFunctions.scala:222](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/classic/DataFrameNaFunctions.scala#L222) — the predicate is `AtLeastNNonNulls(n, cols)` ([nullExpressions.scala](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/nullExpressions.scala)). `dropna` is an ordinary `filter`, not a special operation
- [python/pyspark/sql/column.py:1052](https://github.com/apache/spark/blob/v4.2.0/python/pyspark/sql/column.py#L1052) — `isNull`; `isNotNull` (L1069), `eqNullSafe` (L191)

### Where nulls change results

- [aggregate/Count.scala:49](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/aggregate/Count.scala#L49) — `Count` is itself `nullable = false` (L52): an aggregate over zero rows returns `0`, not null — unlike `sum`, `avg`, `min` and `max`, which return null. Counting a specific column skips nulls; `count(*)` counts rows
- [SparkStrategies.scala:334](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/SparkStrategies.scala#L334) — the **null-aware anti join**: a `LEFT ANTI` join whose key may be null needs special handling, because SQL `NOT IN` semantics say a single null on the right makes the whole result unknown. Enabled by `spark.sql.optimizeNullAwareAntiJoin`. This is the `NOT IN` trap — one null in the subquery and you get no rows at all
- [SortOrder.scala:40](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/SortOrder.scala#L40) — default null ordering: **ascending puts nulls first, descending puts them last** (L45). So `orderBy(col.desc())` does *not* simply reverse `orderBy(col)` when nulls are present. `NullsFirst` (L48) / `NullsLast` (L52) override it

## Chapter notes

Gap analysis against **spark-book Ch 12** (`spark-book/ch12-null-handling.md`).

### Already in spark-book ✅

- `dropna` / `fillna` with `how`, `thresh` and `subset`
- `coalesce` for first-non-null
- Null-safe equality (`<=>` / `eqNullSafe`) and why `==` fails on null keys
- Nulls skipped by aggregates; `count("col")` versus `count("*")`
- Nulls grouped together by `GROUP BY`

### Not in spark-book — needs addition ❌

- **`NaN` is not null, and only `NaNvl` handles it.** A float column can carry both. `coalesce` returns a `NaN` quite happily, `isNull` is false for it, and it survives `dropna`. Anyone doing numeric work meets this eventually, and the chapter treats null as the only missing-value case.
- **Default null ordering is asymmetric.** Ascending puts nulls **first**; descending puts them **last**. So `orderBy(c.desc())` is not the reverse of `orderBy(c)` when nulls are present — a real correctness trap for "top N" queries. `NULLS FIRST` / `NULLS LAST` override it.
- **`NOT IN` with a nullable subquery returns nothing.** SQL semantics make the result unknown if the right side contains a single null, so the anti join yields no rows. Spark has a dedicated null-aware anti join path for it (`spark.sql.optimizeNullAwareAntiJoin`). This is the classic null trap and is absent from the chapter.
- **`how="any"`/`"all"` and `thresh` are the same parameter.** `toMinNonNulls` maps `"any"` → `None` and `"all"` → `Some(1)`; everything becomes `AtLeastNNonNulls(n, cols)`. So `dropna` is an ordinary `filter` with a generated predicate — knowing that makes the three parameters one idea instead of three.
- **`count` is the only aggregate that cannot return null.** `Count.nullable = false`, so an empty group gives `0` while `sum`/`avg`/`min`/`max` give null. Relevant whenever an aggregate result feeds a later expression.
- **Null in a `WHERE` behaves like false — but only there.** `ReplaceNullWithFalseInPredicate` makes that substitution explicitly inside filter and join conditions. Outside a predicate the two are entirely different, and the chapter's rule of thumb needs that boundary or it becomes a wrong generalisation.
- **Nullity is a bit in the row, not a value.** `UnsafeRow`'s null bitmap means the value slot still exists. This explains why null works uniformly across types, and connects to B5: `nullable` is a *declared* property the optimizer trusts, so a wrong declaration yields wrong results rather than an error.
- **ANSI mode changes null-producing paths into errors.** Several operations that returned null in Spark 3.x now raise. Since this chapter is about relying on null semantics, it should say which behaviours are ANSI-dependent — see B3.
- **Writing JSON drops null fields by default.** `spark.sql.jsonGenerator.ignoreNullFields` is `true`, so a read-write-read round trip silently loses null-valued keys. Also relevant to B4.
