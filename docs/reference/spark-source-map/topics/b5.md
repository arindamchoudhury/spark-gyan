## What it is

A schema is a `StructType`: an array of `StructField(name, dataType, nullable, metadata)`. Three surfaces construct the same object — the programmatic builder, a DDL string (`"id BIGINT, name STRING"`), and JSON — and all three converge on the same `DataType` tree, which is what the analyzer resolves against.

The thing worth internalising is that a schema in Spark is a **description used for planning**, not a constraint enforced against data. Two consequences follow, and both surprise people: `nullable = false` is not checked when reading files, and a type mismatch is resolved by *coercion* wherever coercion is legal rather than by rejection. Where Spark does enforce — `createDataFrame` on local Python data, and writes into an existing table — it uses different rules in each case.

## Code path

```
--- three ways to build the same StructType ---

T.StructType([T.StructField("id", T.LongType(), False), ...])   programmatic
"id BIGINT NOT NULL, name STRING"                               DDL string
  → DataType.fromDDL                       [api/types/DataType.scala:137]
      → parseTypeWithFallback              [api/types/DataType.scala:158]
          → parser.parseTableSchema        [api/parser/parsers.scala:52]
          → falls back to parseDataType    [api/parser/parsers.scala:44]
'{"type":"struct","fields":[...]}'                              JSON
  → DataType.fromJson                      [api/types/DataType.scala:179]

--- read path: schema is accepted, not verified ---

spark.read.schema(<StructType>).csv(path)
  → DataSource.getOrInferFileFormatSchema   (B4) — declared schema short-circuits inference
  → analyzer resolves references against it
  → NO nullability check at any point; nullable=false is a planning hint

--- resolution: name matching and type reconciliation ---

Analyzer
  → name resolution honours spark.sql.caseSensitive (default false)
  → TypeCoercion / AnsiTypeCoercion rule sets   [TypeCoercion.scala:47 / AnsiTypeCoercion.scala:76]
       chosen by spark.sql.ansi.enabled
  → Cast                                        [Cast.scala:547]
       canCast          (explicit cast — permissive)      [:223]
       canUpCast        (safe widening only)              [:355]
       canANSIStoreAssign (table insert under ANSI)       [:387]

--- write path into an existing table: the strictest checks live here ---

INSERT INTO / saveAsTable
  → TableOutputResolver.resolveOutputColumns    [TableOutputResolver.scala:90]
       applies spark.sql.storeAssignmentPolicy (ANSI | LEGACY | STRICT)
  → ApplyCharTypePadding                        [ApplyCharTypePadding.scala:37]

--- createDataFrame from local Python data: the one eager verification ---

spark.createDataFrame(rows, schema, verifySchema=True)
  → _make_type_verifier(schema)                 [python/pyspark/sql/types.py:3110]
       raises TypeError / ValueError per row, on the driver, before any job
```

## Relevant configs

| Config | Default | Effect |
|---|---|---|
| `spark.sql.caseSensitive` | `false` | Column resolution is case-**insensitive** by default; a schema declaring `userId` matches `userid` in the data |
| `spark.sql.ansi.enabled` | `true` (4.x) | Selects `AnsiTypeCoercion` over `TypeCoercion` — a different rule set, not a stricter mode of the same one |
| `spark.sql.storeAssignmentPolicy` | `ANSI` | How strictly a write into an existing table checks types: `ANSI`, `LEGACY`, or `STRICT` |
| `spark.sql.legacy.charVarcharAsString` | `false` | When true, `CHAR`/`VARCHAR` behave as plain strings with no padding or length enforcement |
| `spark.sql.legacy.doLooseUpcast` | `false` | Restores the pre-3.0 permissive implicit-cast behaviour |
| `spark.sql.decimalOperations.allowPrecisionLoss` | `true` | Decimal arithmetic may lose precision rather than return null |
| `spark.sql.execution.arrow.pyspark.validateSchema.enabled` | `false` | Validates the Arrow schema against the declared schema on the Arrow conversion path |
| `spark.sql.fileSource.insert.enforceNotNull` | `false` | Whether a file-source insert enforces non-null on declared non-nullable columns |
| `spark.sql.legacy.allowEmptySchemaWrite` | `false` | Whether a zero-column write is permitted |
| `spark.sql.insertNestedTypeCoercion.enabled` | `false` | Extends store-assignment coercion into nested struct fields |
| `spark.sql.parquet.mergeSchema` | `false` | Merge differing per-file schemas via `StructType.merge`; off by default because it is expensive |
| `spark.sql.datetime.java8API.enabled` | `false` | `java.time` types instead of `java.sql` in returned rows |
| `spark.sql.collation.schemaLevel.enabled` | `false` | Schema-level collation (4.x collation work) |

## Chapter notes

Gap analysis against **spark-book Ch 08** (`spark-book/ch08-schema-type-safety.md`).

### Already in spark-book ✅

- `StructType` / `StructField` construction and the DDL-string shorthand
- `inferSchema` cost and why declaring a schema is preferred
- Inspecting a schema at runtime (`printSchema`, `dtypes`, `df.schema`)
- The PySpark type reference including `TimestampNTZType`

### Not in spark-book — needs addition ❌

- **`nullable = false` is not enforced on read.** Nothing in the file-read path validates nullability — it is a planning hint that lets the optimizer skip null checks. Declaring a column non-nullable and then reading a file containing nulls yields nulls in a column the plan believes cannot contain them, which can produce wrong results rather than an error. This is the single most important thing about schemas in Spark and the chapter presents `nullable` as though it were a constraint.
- **Three different "is this cast allowed" rules.** `canCast` (explicit `.cast()`, permissive), `canUpCast` (implicit coercion, safe widening only), and `canANSIStoreAssign` (writing into an existing table). Conflating them is exactly why an expression that works in a `select` fails on `INSERT INTO`. The chapter does not distinguish them.
- **ANSI selects a *different* coercion rule set.** `spark.sql.ansi.enabled` switches between `TypeCoercion` and `AnsiTypeCoercion` — two complete rule objects, not one with a strictness flag. The same query can resolve to different result types on either side of that switch.
- **`spark.sql.caseSensitive` defaults to `false`.** Column resolution is case-insensitive, so a declared `userId` binds to `userid` in the file. Worth stating explicitly in a chapter about matching schemas to data.
- **`CHAR(n)` / `VARCHAR(n)` are erased to `StringType`.** `CharVarcharUtils` rewrites them out of the schema and reinstates padding and length rules as plan-time behaviour. This explains why `CHAR` comparisons behave unlike plain strings and why the declared type does not survive a round trip.
- **`createDataFrame` is the one place Spark verifies eagerly.** `_make_type_verifier` checks type *and range* per row on the driver — a Python `int` exceeding `ByteType` raises there — but only for local Python data with `verifySchema=True`. That asymmetry (strict for local data, permissive for files) is worth naming, since it is where beginners form the wrong intuition that Spark validates schemas generally.
- **`StructType.merge` is the mechanism behind `mergeSchema`.** Field-by-field reconciliation that raises on incompatible types; it is why `mergeSchema=true` is expensive and why it fails on a genuine type conflict rather than picking a winner.
- **DDL strings go through the real SQL parser.** `parseTypeWithFallback` tries `parseTableSchema` then `parseDataType`, so the string is parsed by the same grammar as SQL DDL — meaning type names, backtick quoting and nested syntax match Spark SQL exactly rather than a separate schema mini-language.
- **`df.schema.json()` / `DataType.fromJson` round-trip.** The practical way to pin a schema in a config file or ship it between jobs; the chapter covers only the programmatic and DDL forms.
