## What it is

`df.groupBy(cols)` does not aggregate anything — it returns a `RelationalGroupedDataset`, a builder holding the source plan, the grouping expressions, and a *group type* (`GroupBy`, `Rollup`, `Cube`, `Pivot`). Only `agg` (or a shorthand like `count()`) turns that into an `Aggregate` logical node.

The interesting part is below the logical plan. One `Aggregate` node normally becomes **two physical operators** — a partial aggregate before the shuffle and a final aggregate after it — which is Spark's map-side combine and the reason `groupBy().count()` on a billion rows does not ship a billion rows across the network. Which physical operator is chosen depends on the aggregate buffer's types, and each has its own memory-exhaustion fallback. `DISTINCT` inside an aggregate is a different shape again: it is rewritten into an `Expand` that multiplies the input rows before aggregating.

```
df.groupBy("dept").agg(F.sum("salary"), F.countDistinct("id"))

  → Dataset.groupBy(cols)                    [classic/Dataset.scala:1011]

  → RewriteDistinctAggregates               [optimizer/RewriteDistinctAggregates.scala]
        rewrites distinct aggregates into an Expand that emits one row

        final    = aggregateExpressions.copy(mode = Final)        [:158]

        if buffer types are mutable          → HashAggregateExec        [:85]
```

### Pivot — the one that runs a hidden job

- [classic/RelationalGroupedDataset.scala:674](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/classic/RelationalGroupedDataset.scala#L674) — `collectPivotValues`: `pivot(col)` without an explicit value list runs a **distinct + limit + collect** (L678) to discover the values, then raises if there are more than `spark.sql.pivotMaxValues` (L684). ## Chapter notes

Gap analysis against **spark-book Ch 09** (`spark-book/ch09-aggregations-groupby.md`).

### Already in spark-book ✅

- `groupBy().agg()` as the core pattern, and `GroupedData` as an intermediate object
- The built-in aggregate functions (`count`, `sum`, `avg`, `min`, `max`, `countDistinct`)
- Multiple aggregations in a single `agg()` call
- `F.when()` for conditional counting
- The SQL `GROUP BY ... HAVING` equivalent

### Not in spark-book — needs addition ❌

- **One `Aggregate` becomes two physical operators, and that is map-side combine.** `planAggregateWithoutDistinct` builds a `Partial` aggregate, then the shuffle, then a `Final` aggregate. This is why `groupBy().count()` on a huge input is cheap, and why `HashAggregateExec` legitimately appears twice in an `EXPLAIN` — which otherwise looks like a bug. The chapter teaches the API without the shape of the plan it produces.
- **`countDistinct` changes the plan shape, and multiple distincts multiply the data.** A single distinct aggregate becomes a four-stage plan; multiple distinct aggregates are rewritten by `RewriteDistinctAggregates` into an `Expand` that emits one row per distinct group per input row before aggregating. This is the concrete cost model behind "avoid several `countDistinct`s in one query", and the chapter presents `countDistinct` as just another function.
- **Three physical aggregate operators, chosen by buffer type.** `HashAggregateExec` (mutable fixed-width buffers — the fast path), `ObjectHashAggregateExec` (`collect_list`, `percentile`, typed UDAFs), `SortAggregateExec` (the fallback). Which one you get is not a tuning decision but a consequence of the functions used, and it explains why adding one `collect_list` to an otherwise cheap aggregate changes its performance profile.
- **Both hash operators fall back to sorting, on different triggers.** `HashAggregateExec` falls back on memory pressure, per task, mostly silently. `ObjectHashAggregateExec` falls back after **128 groups** by default — a group *count*, not a memory measurement, which surprises people who assume the threshold is size-based.
- **`numTasksFallBacked` is a visible Spark UI metric.** The direct way to confirm an aggregate is spilling rather than guessing at it. Belongs beside any performance discussion in this chapter.
- **`pivot()` without an explicit value list runs a hidden extra job.** `collectPivotValues` does a distinct-limit-collect to discover values, capped by `spark.sql.pivotMaxValues` (10000). Passing the values explicitly eliminates a full pass over the data — a large, easy win that is invisible from the API surface.
- **`rollup`, `cube` and `groupingSets` return the same `RelationalGroupedDataset`.** They differ only in group type, so everything the chapter teaches about `agg` applies unchanged. Worth one line, since they otherwise look like separate APIs to learn.
- **`spark.sql.shuffle.partitions` is *the* knob for a `groupBy`.** It sets the post-shuffle partition count between the partial and final aggregates. The chapter does not connect the aggregation pattern to the config that governs its cost.
- **Aggregate pushdown into Parquet/ORC footers exists and is off by default.** `min`/`max`/`count` can sometimes be answered from file statistics without scanning, via `spark.sql.parquet.aggregatePushdown`.
- **`avg` and `mean` are the same function.** Both map to `Average` in `FunctionRegistry`; there is no behavioural difference, only naming.
