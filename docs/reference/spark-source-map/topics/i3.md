## What it is

A Python UDF is not an expression Spark can evaluate. It is a **callback into a separate operating-system process**, and every design consequence follows from that: rows must be serialized out of the JVM, a Python worker computes, results are serialized back. Catalyst cannot see inside the function, so it cannot push filters through it, reorder around it, or fold it away.

What changed in Spark 4.2.0 is the *transport*. `spark.sql.execution.pythonUDF.arrow.enabled` now defaults to **`true`**, so a plain `@udf` is Arrow-serialized rather than pickled row-by-row. The Python-JVM boundary still exists — but the "plain UDF is catastrophically slower than a pandas UDF" gap the books measure was largely a measurement of pickle, not of the boundary itself.

The eval-type integer is the thing worth internalising: every UDF variant is one number, chosen at registration, that selects both the JVM-side runner and the Python-side wrapper.

## Key source locations

All anchors verified against the `v4.2.0` tag on 2026-07-18.

### Registration — and the 4.2.0 default flip

- [python/pyspark/sql/udf.py:102](https://github.com/apache/spark/blob/v4.2.0/python/pyspark/sql/udf.py#L102) — when `useArrow is None`, the decision reads `spark.sql.execution.pythonUDF.arrow.enabled`, which is **`true`** in 4.2.0. An explicit `useArrow=` overrides it (L112)
- [python/pyspark/sql/udf.py:118](https://github.com/apache/spark/blob/v4.2.0/python/pyspark/sql/udf.py#L118) — if Arrow is requested but PyArrow or pandas is missing, Spark **silently downgrades** to the non-Arrow path with a `RuntimeWarning`. So performance can differ between environments with identical code, and the only signal is a Python warning
- [python/pyspark/util.py:657](https://github.com/apache/spark/blob/v4.2.0/python/pyspark/util.py#L657) — `PythonEvalType`: `SQL_BATCHED_UDF` = 100, `SQL_ARROW_BATCHED_UDF` = 101 (L658), `SQL_SCALAR_PANDAS_UDF` = 200 (L660), grouped-map variants at 201/209, iterator variants at 215/216. **This integer is the whole taxonomy** — it appears in plans, in the worker dispatch, and in error messages

### The expression, and two properties that constrain the optimizer

- [catalyst/expressions/PythonUDF.scala:96](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/PythonUDF.scala#L96) — the `PythonUDF` expression
- [catalyst/expressions/PythonUDF.scala:89](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/PythonUDF.scala#L89) — **`nullable = true`, unconditionally.** A UDF's output is always nullable regardless of its declared return type, so downstream null checks can never be optimized away (connects to B5 and B9)
- [catalyst/expressions/PythonUDF.scala:85](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/PythonUDF.scala#L85) — `deterministic = udfDeterministic && children.forall(_.deterministic)`. Marking a UDF non-deterministic blocks the optimizer from reordering or duplicating it — which is required for correctness with randomness, and costs optimization when set unnecessarily

### Planning — UDFs are pulled out of the expression tree

- [python/ExtractPythonUDFs.scala:162](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/python/ExtractPythonUDFs.scala#L162) — the rule that lifts UDFs into dedicated plan nodes; `collectEvaluableUDFs` at L251. UDFs of the **same eval type** are batched into one node, so mixing a plain UDF with a pandas UDF in one `select` produces *two* nodes and two round trips to Python. Keeping a chain to one UDF flavour is a real optimization
- [python/BatchEvalPythonExec.scala:37](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/python/BatchEvalPythonExec.scala#L37) — the pickle path; [python/ArrowEvalPythonExec.scala:77](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/python/ArrowEvalPythonExec.scala#L77) — the Arrow path. Which appears in your plan tells you which transport you got

### Execution — the worker process

- [python/PythonUDFRunner.scala:143](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/python/PythonUDFRunner.scala#L143) and [python/ArrowPythonRunner.scala:97](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/python/ArrowPythonRunner.scala#L97) (base at L33) — the JVM side of the socket protocol
- [SparkEnv.scala:166](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/SparkEnv.scala#L166) — `createPythonWorker`. Workers are keyed by `(pythonExec, workerModule, daemonModule, envVars)` (L173), forked from a daemon when `spark.python.use.daemon` is on, and **reused across tasks** when `spark.python.worker.reuse` is on (default). Worker reuse is what makes per-partition initialisation (loading a model once) actually pay off
- [python/pyspark/worker.py:1112](https://github.com/apache/spark/blob/v4.2.0/python/pyspark/worker.py#L1112) — the Python side dispatches on `eval_type` (L1112–L1122), selecting the wrapper that shapes arguments: `wrap_scalar_pandas_udf` (L381) hands your function a `pd.Series`, the Arrow variants hand it `pyarrow` arrays

## Chapter notes

Gap analysis against **spark-book Ch 15** (`spark-book/ch15-udfs.md`).

### Already in spark-book ✅

- The Python-JVM boundary and why it costs
- `@F.udf` versus `@F.pandas_udf`, with the Series→Series and Iterator variants
- Iterator UDFs for once-per-partition initialisation (model loading)
- Testing a UDF locally via `.func`
- The performance hierarchy from built-ins downward
- A performance table listing the Arrow-native UDF as `useArrow=True`, Spark 4.1+

### Not in spark-book — needs addition ❌

- **The Arrow default flipped in 4.2.0, so the chapter's framing is now inverted.** `spark.sql.execution.pythonUDF.arrow.enabled` is `true`, meaning a plain `@udf` is Arrow-serialized *by default*. The chapter presents Arrow as opt-in via `useArrow=True`, and quotes "typically 5–10× faster" for pandas UDFs — a figure measured against per-row pickle. The hierarchy still holds directionally, but both the defaults and the multipliers need re-measuring on 4.2.0.
- **Arrow silently downgrades when PyArrow or pandas is missing.** The registration path catches `ImportError` and falls back with only a `RuntimeWarning`. Identical code can therefore run at very different speeds across environments, which is worth knowing before benchmarking.
- **The eval-type integer is the real taxonomy.** `PythonEvalType` assigns each variant a number (100 batched, 101 Arrow-batched, 200 scalar pandas, 201/209 grouped map, 215/216 iterator forms). It appears in plans and error messages, and it is what the Python worker dispatches on — so it is the fastest way to confirm which UDF flavour actually ran.
- **A UDF's output is always nullable.** `PythonUDF.nullable = true` unconditionally, whatever return type you declare. Downstream null checks therefore cannot be optimized away — a concrete, permanent optimizer cost beyond serialization, and it connects to B5's point that nullability is a planning property.
- **Mixing UDF types in one `select` costs an extra round trip.** `ExtractPythonUDFs` groups UDFs of the *same* eval type into one node, so a plain UDF alongside a pandas UDF produces two nodes and two crossings of the boundary. Keeping a chain to one flavour is a real and easily-missed optimization.
- **Non-deterministic UDFs block optimizer rewrites.** `deterministic` gates reordering and duplication. Marking a UDF non-deterministic is necessary when it uses randomness and costly when it does not — the chapter does not mention the flag.
- **Worker reuse is why per-partition initialisation works.** `spark.python.worker.reuse` (default on) keeps the process alive across tasks, and workers are keyed by executable and environment. Without it the Iterator-UDF model-loading pattern the chapter teaches would reload per task.
- **`spark.executor.pyspark.memory` is separate from executor heap.** Python workers live outside the JVM, so their memory is not part of `spark.executor.memory`. A common cause of container OOM kills with heavy pandas UDFs.
- **Batch size is capped by bytes as well as rows.** `maxRecordsPerBatch` (10000) and `maxBytesPerBatch` (64MB) both apply; for wide rows the byte cap binds first, so tuning only the row count does nothing.
- **`BatchEvalPythonExec` versus `ArrowEvalPythonExec` in the plan tells you which transport ran.** The direct way to verify Arrow is actually in use rather than assuming it from the config.
