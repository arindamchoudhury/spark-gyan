## What it is

`spark.sql("…")` is not a second engine. The string is parsed by ANTLR into the *same* `LogicalPlan` the DataFrame API builds, and from that point everything — analysis, optimization, physical planning, execution — is shared. Whatever you can say in one surface you can say in the other, and the plans are indistinguishable afterwards.

Two things are genuinely specific to the SQL surface, and both are where the real content of this topic lives. First, **name resolution**: a bare identifier has to be resolved against temp views, then the catalog, in a defined order, and the rules for temp views versus global temp views versus tables are not symmetric. Second, **parameter binding**: since Spark 3.4 `spark.sql` accepts arguments, which is the supported answer to SQL injection rather than string interpolation.

### Parameter binding — the injection fix

- [analysis/parameters.scala:76](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/analysis/parameters.scala#L76) — `NameParameterizedQuery`; `PosParameterizedQuery` at L100, `GeneralParameterizedQuery` at L119

### Name resolution — the asymmetric part

- [catalog/SessionCatalog.scala:1103](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/catalog/SessionCatalog.scala#L1103) — `lookupRelation`, and the branch order is the whole story:
  1. database == `global_temp` → `GlobalTempViewManager`
  2. **a database was given, or the name is not a temp view** → the external catalog (a real table)
  3. otherwise → the local temp view

  So an unqualified name prefers a **temp view over a table of the same name**, while any qualification skips temp views entirely. `db.name` never finds a temp view.
- [catalog/SessionCatalog.scala:305](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/catalog/SessionCatalog.scala#L305) — `tempViews` is a plain `mutable.HashMap` on the `SessionState`. Not persisted, not shared — it dies with the session, which is the concrete reason temp views are session-scoped (contrast the global temp DB, which lives on `SharedState`; see B2)
- [catalog/SessionCatalog.scala:845](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/catalog/SessionCatalog.scala#L845) — `createTempView`; raises when the name exists and `overrideIfExists` is false (L850) — the mechanical difference between `createTempView` and `createOrReplaceTempView`

## Chapter notes

Gap analysis against **spark-book Ch 11** (`spark-book/ch11-spark-sql.md`).

### Already in spark-book ✅

- SQL and the DataFrame API as two surfaces over one Catalyst engine, producing the same plan
- `createOrReplaceTempView` and `spark.sql()`
- Mixing via `selectExpr` and `F.expr`
- The catalog basics (`listTables`, `dropTempView`)
- SQL injection named as a risk
- `createTempView` raising when the name exists, versus `createOrReplaceTempView`
- Written order versus execution order (`SELECT` after `WHERE`/`GROUP BY`)

### Not in spark-book — needs addition ❌

- **Parameterized SQL is the fix for the injection risk the chapter raises.** `spark.sql(query, args)` binds arguments as literal expressions via the `BindParameters` analyzer rule, *after* parsing — so a value structurally cannot become SQL syntax. The chapter identifies the danger and then recommends only "use the DataFrame API instead", which concedes the SQL surface unnecessarily. Note `sql(text)` is literally defined as `sql(text, Map.empty)`, so parameters cost nothing.
- **Name resolution is asymmetric, and this is the sharp edge of temp views.** `lookupRelation` prefers a temp view over a table of the same name for an *unqualified* name, but any qualification (`db.name`) skips temp views entirely. So a temp view can silently shadow a real table, and a qualified reference can never reach a temp view — neither is guessable from the API.
- **Temp views are a `HashMap` on `SessionState`.** That is precisely why they are session-scoped, and it connects to B2's `SharedState`/`SessionState` split: `createGlobalTempView` puts the view in `SharedState`'s global temp database instead, which is why it outlives the session. The chapter states the scoping rule without the mechanism, so the global variant looks arbitrary.
- **Views store SQL text and re-analyze on use.** A persisted view re-resolves against the current schema each time, so an underlying column change is picked up (or errors). `spark.sql.legacy.storeAnalyzedPlanForView` freezes the plan instead. Spark 4.x also adds view schema *binding modes* via `ALTER VIEW … WITH SCHEMA`. None of this is in the chapter, and it is what determines whether a view breaks when its source changes.
- **`F.expr` and `selectExpr` use the full SQL parser.** Both call `parseExpression` on the same grammar as `spark.sql`. The chapter says the namespace is SQL rather than Python, which is right, but the stronger and more useful statement is that it is *the same parser* — so anything valid in a SQL expression is valid there.
- **`spark.sql.parser.quotedRegexColumnNames` turns backtick names into regex patterns.** A rarely-known switch that makes `` SELECT `col_.*` `` select by pattern — surprising if enabled unknowingly.
- **`spark.catalog` is a typed API, not just `listTables`.** `tableExists`, `listColumns`, `listFunctions` and cache management all live there; the chapter shows two methods.
