## What it is

Every keyed aggregation on an RDD — `reduceByKey`, `aggregateByKey`, `foldByKey`, `groupByKey`, `combineByKey` — is one function with different arguments. They all call `combineByKeyWithClassTag`, which takes three lambdas:

| Function | Role |
|---|---|
| `createCombiner: V => C` | start an accumulator from the first value for a key |
| `mergeValue: (C, V) => C` | fold another value into an accumulator |
| `mergeCombiners: (C, C) => C` | merge two accumulators — used **across partitions** |

Plus one boolean, `mapSideCombine`, that decides whether accumulation happens before the shuffle or only after it. That boolean is the entire performance story of this topic: `reduceByKey` passes `true`, `groupByKey` passes `false`, and everything people say about their relative cost follows from that single argument.

### One implementation, five public names

- [rdd/RDD.scala:2174](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/RDD.scala#L2174) — `implicit def rddToPairRDDFunctions`: keyed operations are **not** methods on `RDD`. They arrive by implicit conversion when the element type is a pair, which is why they are invisible in `RDD`'s own API listing and why the error when your type is wrong is confusing
- [rdd/PairRDDFunctions.scala:72](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/PairRDDFunctions.scala#L72) — `combineByKeyWithClassTag`: the single implementation. The `mapSideCombine: Boolean = true` parameter is defaulted **on**
- [rdd/PairRDDFunctions.scala:305](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/PairRDDFunctions.scala#L305) — `reduceByKey` is one line (L306): the same function serves as `mergeValue` *and* `mergeCombiners`, which is exactly why it must be associative and commutative — Spark applies it both within and across partitions
- [rdd/PairRDDFunctions.scala:159](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/PairRDDFunctions.scala#L159) — `aggregateByKey`: separate `seqOp`/`combOp`, so the accumulator type may differ from the value type. `foldByKey` (L208) is the same idea with a zero value
- [rdd/PairRDDFunctions.scala:497](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/PairRDDFunctions.scala#L497) — `groupByKey`, which passes **`mapSideCombine = false`** (L505). One argument is the whole difference

### The source's own warning

- [rdd/PairRDDFunctions.scala:490](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/PairRDDFunctions.scala#L490) — the scaladoc above `groupByKey` says it outright: *"This operation may be very expensive… using `aggregateByKey` or `reduceByKey` will provide much better performance"*, and that grouping holds all values for a key **in memory**, so *"if a key has too many values, it can result in an `OutOfMemoryError`"*.

  Note the asymmetry this creates: the combine path spills to disk, but `groupByKey`'s per-key `Iterable` must fit in memory. `reduceByKey` on skewed data degrades; `groupByKey` on skewed data **fails**

### The shuffle-avoiding branch people miss

- [rdd/PairRDDFunctions.scala:92](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/PairRDDFunctions.scala#L92) — `if (self.partitioner == Some(partitioner))` → `mapPartitions`, **no `ShuffledRDD` at all**. An RDD already partitioned by the same partitioner aggregates entirely locally. This is the RDD-level version of the negotiation `EnsureRequirements` performs for DataFrames (I5), and it is why `partitionBy` before repeated keyed aggregations pays off
- [rdd/PairRDDFunctions.scala:98](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/PairRDDFunctions.scala#L98) — otherwise a `ShuffledRDD`, with `setMapSideCombine` (L101) carrying the flag through to the shuffle writer ([ShuffledRDD.scala:73](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/ShuffledRDD.scala#L73))

### Execution — and where the memory actually goes

- [Aggregator.scala:32](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/Aggregator.scala#L32) — holds the three functions

### What this topic is actually for ❗

- **Five API names, one implementation, one decisive boolean.** `reduceByKey`, `aggregateByKey`, `foldByKey`, `groupByKey` and `combineByKey` all reach `combineByKeyWithClassTag`; the only structural difference between the fast and slow cases is `mapSideCombine`. Learning the three-lambda signature once explains all of them, and makes the folklore ("prefer reduceByKey") a derivation rather than a rule.
- **`reduceByKey` degrades under skew; `groupByKey` fails.** The combine path uses `ExternalAppendOnlyMap` and spills to disk. `groupByKey` materialises every value for a key as an in-memory `Iterable`, and the source scaladoc says plainly that a hot key gives an `OutOfMemoryError`. That difference in *failure mode*, not just speed, is the real argument.
- **Because `reduceByKey`'s function is used both within and across partitions, it must be associative and commutative.** `reduceByKey(f)` passes `f` as `mergeValue` and `mergeCombiners`. This is the mechanical reason behind the requirement that is usually asserted without justification.
- **An already-partitioned RDD skips the shuffle entirely.** `combineByKeyWithClassTag` checks `self.partitioner == Some(partitioner)` and falls back to `mapPartitions`. The RDD-level counterpart of I5's negotiated partitioning, and the payoff for `partitionBy` when several aggregations share a key.
- **`aggregateByKey` exists for when the accumulator type differs from the value type** — computing an average needs `(sum, count)`, which `reduceByKey` cannot express without allocating pairs first. Frequently the right answer where people reach for `groupByKey`.
- **Spill is observable.** `Aggregator.updateMetrics` reports spill bytes and records to the UI (I7), so "is this aggregation spilling" is a question with a direct answer rather than a guess.
- **This is the RDD-level twin of B6.** `HashAggregateExec`'s partial/final split is the DataFrame version of `mapSideCombine`, and its fallback to sort-based aggregation mirrors `ExternalAppendOnlyMap` spilling. Reading the two together makes both concrete — and shows that the DataFrame API's advantage here is that it makes the *right* choice automatically.
