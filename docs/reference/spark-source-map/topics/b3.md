## What it is

The DataFrame API is Spark's primary structured data interface: a distributed, schema-typed table of `Column` expressions that compiles down to a logical plan tree. Every transformation method — `select`, `filter`, `withColumn`, `drop`, `distinct`, `orderBy` — appends a node to that tree without touching any data. Data moves only when an action fires (`show`, `collect`, `count`, `write`). The execution path is: method call → logical plan node → `HybridAnalyzer` resolution (fixed-point by default) → `Optimizer` rewrites → physical planning → `CollapseCodegenStages` inserts `WholeStageCodegenExec` → `RDD[InternalRow]` execution.

## Code path

```
df.filter(cond)      → Filter(cond.expr, logicalPlan)
df.select(cols)      → Project(cols.map(_.named), logicalPlan)
df.withColumn(n, c)  → withColumns(Seq(n), Seq(c))
                     → Project(UnresolvedStarWithColumns(names, exprs), logicalPlan)
df.drop("col")       → eager analysis → Project(surviving attrs)
df.drop(F.col("c"))  → DataFrameDropColumns(dropList, logicalPlan)   [lazy, ignores missing]
df.distinct()        → (api) dropDuplicates()          [4.2.0: impl moved to sql/api]
                     → Deduplicate(groupCols, logicalPlan)
df.orderBy(cols)     → sortInternal(global=true, cols)
                     → Sort(sortOrder, global=true, logicalPlan)
```

Analysis: `QueryExecution.executeAndCheck` → `HybridAnalyzer.apply` → fixed-point `Analyzer.batches` → Resolution batch (ResolveRelations → DeduplicateRelations → ResolveReferences → ResolveAliases → type coercion, up to `maxIterations=100`)

Execution preparations sequence (`QueryExecution.preparations`): `InsertAdaptiveSparkPlan` (if inserted, subsequent rules become no-ops) → ... → `CollapseCodegenStages` (inserts WSCG) → `ReuseExchangeAndSubquery`.

### Not in spark-book — needs addition ❌

- **`withColumn` compiles to the same plan node as `withColumns`** — `withColumn(n, c)` is a strict one-liner that calls `withColumns(Seq(n), Seq(c))`. Both produce `Project(UnresolvedStarWithColumns(...))`. The `UnresolvedStarWithColumns` expression type (introduced to fix the N-node problem) does the expansion during analysis via its `expandStar` method — replacing matching columns and appending new ones in a single `Project`. The book says "chaining `withColumn` adds a node per call" which is correct, but does not explain the mechanism or the API layer delegation.

- **Two `drop` overloads behave differently** — `drop(String*)` forces eager analysis (`queryExecution.analyzed.output`) at the call site, using case-insensitive column resolution. `drop(Column*, ...)` is lazy: it produces a `DataFrameDropColumns` node that `ResolveDataFrameDropColumns` rewrites to a `Project`, silently skipping any non-existent columns. Practitioners who expect `drop` to fail on a missing column will be surprised by the silent no-op in both overloads.

- **`distinct()` produces `Deduplicate`, not `Distinct`** — `distinct()` is purely an alias for `dropDuplicates()`; the Catalyst plan node is `Deduplicate(groupCols, logicalPlan)`. There is no `Distinct` operator. Knowing the actual node name is useful when reading `EXPLAIN` output or Spark UI plan trees. *(Corrected 4.2.0: the implementation moved from `classic` to `sql/api` and is now `dropDuplicates()` with no argument — the 4.1.2 trace recorded `dropDuplicates(this.columns)`. Same observable behaviour, different call.)*

- **`describe` is not a plan node — it delegates to `summary`** — `describe(cols)` calls `selected.summary("count", "mean", "stddev", "min", "max")`. Practitioners who want different statistics (e.g. percentiles) should call `df.summary("25%", "50%", "75%")` directly.

- **`printSchema(level: Int)` overload exists** — `df.printSchema(2)` limits display to N levels of nested struct depth. Not widely known and not in the book.

- **`show(n)` fetches N+1 rows** — `showString` calls `take(numRows + 1)` so it can detect whether more rows exist and append `...` without a second network call. `df.show(20)` collects up to 21 rows to the driver.

- **`HybridAnalyzer` is the real analysis entry point in Spark 4.x** — `Analyzer.executeAndCheck` delegates to `HybridAnalyzer.apply`, which dispatches between fixed-point (default), single-pass (`spark.sql.analyzer.singlePassResolver.enabled`), and dual-run (validation) modes. Understanding this three-mode dispatch matters for anyone investigating Spark 4.x analysis behavior or benchmarking the new single-pass resolver.

- **Single-pass resolver (`enabledTentatively`) is new in Spark 4.1** — `spark.sql.analyzer.singlePassResolver.enabledTentatively=true` runs the single-pass resolver for supported queries and falls back to fixed-point for unsupported ones. It is the stepping-stone toward making single-pass the default and is worth knowing when benchmarking Spark 4.1 analysis performance.

- **Caching has a 4 MB per-batch cap independent of `batchSize`** — `DefaultCachedBatchSerializer` exits batch accumulation when either `rowCount >= 10000` OR `totalSize >= 4 MB`. A single wide row can produce tiny batches in row-count terms. This explains unexpectedly many cached batches in `EXPLAIN` output for very wide schemas.

- **Vectorized cache reads are primitive-type only** — `supportsColumnarOutput` returns `true` only for Boolean, Byte, Short, Int, Long, Float, Double. String, Array, Map, and Struct columns always use row-by-row deserialization via `GenerateColumnAccessor` even when `spark.sql.inMemoryColumnarStorage.enableVectorizedReader=true`. Important caveat for caching DataFrames with complex-type columns.

- **WSCG `maxFields` counts nested fields recursively** — `isTooManyFields` recurses through `StructType`, `MapType`, `ArrayType`, and `UserDefinedType`. A DataFrame with a single struct column containing 101 leaf fields will disable WSCG for that operator. Practitioners adding struct columns iteratively can hit this limit unexpectedly.

- **Codegen stage IDs appear in JVM profiler traces** — `spark.sql.codegen.useIdInClassName=true` (default) embeds the stage counter in the generated class name (`GeneratedIteratorForCodegenStage3`). When profiling with async-profiler or JFR, flame graph hot methods map directly back to specific physical plan stages by ID.

- **`===` logs a warning for trivially-true predicates** — `Column.checkTrivialPredicate` compares normalized `ColumnNode` representations. `df.filter(F.col("a") === F.col("a"))` logs a WARN. Worth knowing when debugging unexpected warnings in tests.

- **Analysis errors fire before any job runs.** `CheckAnalysis.checkAnalysis` raises `AnalysisException` at resolution time, so a misspelled column fails instantly with nothing in the Spark UI, while a bad cast survives analysis and fails inside a task. The chapter teaches lazy evaluation as "nothing happens until an action" — true for *execution*, but resolution errors break that rule, and the distinction is what makes the two failure modes make sense.

- **`withAction` is what creates the SQL-tab entry.** Every action routes through `withAction` → `SQLExecution.withNewExecutionId`. Chained transformations with no action produce no UI entry at all — worth stating in a chapter that teaches laziness.

- **`explain()` shows the pre-AQE plan.** `AdaptiveSparkPlanExec.finalPhysicalPlan` is only determined after execution, so the plan printed before running is not the plan that ran. The chapter covers AQE's existence but not this discrepancy, which is a routine source of confusion when comparing `explain()` output against the Spark UI.

- **`collect()` deserializes via an `ExpressionEncoder`.** `collectFromPlan` builds a deserializer and maps it over `executeCollect()`. The chapter describes `InternalRow` and the three row representations well but does not name the encoder as the thing that converts between them.

- **The Connect `DataFrame` is a separate class.** `pyspark.sql.connect.dataframe.DataFrame` builds protobuf relations rather than wrapping a JVM object; it has no `_jdf`. Concrete grounding for the classic-vs-Connect discussion the chapter already gestures at.

- **The `classic` / `api` split is migrating method bodies between modules** — `distinct()` moved from `sql/core`'s `classic/Dataset` to `sql/api`'s `Dataset` between 4.1.2 and 4.2.0, leaving a bare `super.distinct()` override behind. Worth knowing when reading stack traces or navigating the source: a method absent from `classic/Dataset.scala` is not missing, it is inherited. Expect more of these moves across 4.x.
