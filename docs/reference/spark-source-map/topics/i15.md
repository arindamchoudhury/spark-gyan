## What it is

Iceberg and Delta solve the same problem and disagree on the central design choice, which is what makes tracing them together worthwhile.

**Delta** (I8) keeps an ordered log of JSON commits; the current state is the log replayed, and atomicity comes from *exactly one writer being able to create file `N.json`*.

**Iceberg** keeps a **tree**: a catalog holds a pointer to the current metadata file; that file names a snapshot; the snapshot names a manifest list; each manifest lists data files with their statistics. Atomicity comes from *swapping the catalog's pointer* — a compare-and-swap on `(base, new)` metadata, not on a filename.

That difference cascades. Because Iceberg's current state is one pointer rather than a replay, the catalog is the coordination point — which is why the REST Catalog specification matters so much for interoperability, and why "which catalog" is the first question for an Iceberg table where it is barely a question for Delta.

### Spark integration — the same plugin mechanism as Delta

### The metadata tree

- [core/.../TableMetadata.java:54](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/core/src/main/java/org/apache/iceberg/TableMetadata.java#L54) — the metadata file: schema, partition specs, snapshot list, and `currentSnapshotId` (L258). **This file is immutable**; every change writes a new one and repoints the catalog
- [api/.../Snapshot.java:34](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/api/src/main/java/org/apache/iceberg/Snapshot.java#L34) — `manifestListLocation()` (L171) and `allManifests(io)` (L73). A snapshot does not list data files; it lists *manifests*, which is the level of indirection Delta does not have
- [api/.../ManifestFile.java:29](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/api/src/main/java/org/apache/iceberg/ManifestFile.java#L29) and [api/.../DataFile.java:35](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/api/src/main/java/org/apache/iceberg/DataFile.java#L35) — manifests carry partition-value *bounds*; data files carry per-column stats

### Planning — pruning happens twice

- [core/.../ManifestGroup.java:177](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/core/src/main/java/org/apache/iceberg/ManifestGroup.java#L177) — `planFiles()`
- [core/.../ManifestGroup.java:286](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/core/src/main/java/org/apache/iceberg/ManifestGroup.java#L286) — `ManifestEvaluator.forPartitionFilter`, cached per spec (L279). **Entire manifests are skipped without being opened**, using the partition bounds recorded in the manifest list; only surviving manifests are read, and their data-file stats then prune individual files.

  This two-level pruning is the architectural payoff of the extra indirection: on a large table, planning reads a small fraction of the metadata. Delta reconstructs state from the log and prunes on `AddFile` stats — one level

### Commit — compare-and-swap, not filename creation

- [core/.../SnapshotProducer.java:459](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/core/src/main/java/org/apache/iceberg/SnapshotProducer.java#L459) — `commit()`, wrapped in a retry loop (L465) that retries **only** on `CommitFailedException` (L471)
- [core/.../BaseMetastoreTableOperations.java:109](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/core/src/main/java/org/apache/iceberg/BaseMetastoreTableOperations.java#L109) — `commit(base, metadata)`: if `base` is no longer current, it throws `CommitFailedException("Cannot commit: stale table metadata")` (L113). **The catalog performs the swap**, so the atomicity guarantee is the catalog's, not the filesystem's — which is precisely why Iceberg works uniformly on object stores where Delta's rename semantics are awkward (B4, I8)

### Interoperability

- [core/.../rest/RESTCatalog.java:47](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/core/src/main/java/org/apache/iceberg/rest/RESTCatalog.java#L47) — the REST catalog client. Because commits go through the catalog rather than the filesystem, a catalog *service* can coordinate writers across engines — the mechanism behind Iceberg's multi-engine story

### Hidden partitioning and schema evolution

- [api/.../PartitionSpec.java:53](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/api/src/main/java/org/apache/iceberg/PartitionSpec.java#L53) — a spec maps source columns through `Transform`s (L39–L41). Partition values are **derived**, so queries filter on the source column and Iceberg applies the transform itself — no `WHERE dt = ...` alongside `WHERE ts = ...`, and no directory layout leaking into queries. `TableMetadata` holds a *list* of specs, which is how partitioning evolves without rewriting data
- [api/.../Schema.java:56](https://github.com/apache/iceberg/blob/apache-iceberg-1.11.0/api/src/main/java/org/apache/iceberg/Schema.java#L56) — columns are identified by **field ID** (L164–L168), not by name or position. Renaming a column is a metadata edit; dropping and re-adding a name does not silently resurrect old data

## Chapter notes

### Points the chapter should not miss ❗

- **The design difference is one sentence: Delta replays a log, Iceberg follows a pointer to a tree.** Everything else — why the catalog matters, why Iceberg suits object stores, why planning scales differently — falls out of that. Teach the contrast rather than two separate systems.
- **Atomicity is the catalog's, not the filesystem's.** Delta relies on exactly one writer creating `N.json`; Iceberg relies on a compare-and-swap of the metadata pointer, performed by the catalog. This is why the catalog choice is Iceberg's first architectural decision and why a REST catalog enables cross-engine coordination.
- **Pruning happens at two levels.** Manifests are skipped whole on partition bounds before being opened; surviving manifests then prune data files on column stats. That extra indirection is the reason planning stays cheap on very large tables, and it is the concrete answer to "why is Iceberg's metadata more complex".
- **Hidden partitioning means queries never mention partition columns.** The spec maps a source column through a transform, so filtering on the source column is enough — no derived `dt` column, no leaked directory layout. And because `TableMetadata` keeps a *list* of specs, partitioning can evolve without rewriting existing data. This is Iceberg's most visible advantage over Hive-style layouts and over Delta's directory partitioning.
- **Columns have IDs, not names.** Rename is metadata-only; drop-then-add does not resurrect old data. Contrast with Delta, where column mapping is an opt-in table feature.
- **A commit failure is normal and retried.** `CommitFailedException` on stale metadata triggers a bounded retry — the same optimistic-concurrency shape as Delta's `ConflictChecker`, reached by a different route.
- **Iceberg tables are catalog-addressed, Delta tables are usually path-addressed.** A practical difference that shows up immediately in setup and in how the two are referenced in SQL.
