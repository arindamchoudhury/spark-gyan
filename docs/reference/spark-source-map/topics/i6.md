## What it is

Caching answers one question: this DataFrame is used more than once — should the second use recompute it or read it back?

Three things make that harder than it sounds, and each is a separate mechanism. **Registration is by plan, not by variable**: the `CacheManager` holds a list of cached plans and matches a new query against them with `sameResult`, so whether you get a cache hit depends on plan equivalence rather than on reusing a Python object. **Materialization is lazy** for `df.cache()` and eager for `CACHE TABLE`. And **retention is not guaranteed**: cached blocks live in a memory region that execution can evict from, so a cached DataFrame can silently become a recomputation.

## Key source locations

All anchors verified against the `v4.2.0` tag on 2026-07-18.

### Entry points, and the default that differs from RDDs

- [classic/Dataset.scala:1631](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/classic/Dataset.scala#L1631) — `cache()` = `persist(conf.defaultCacheStorageLevel)`
- [SQLConf.scala:2312](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/internal/SQLConf.scala#L2312) — `spark.sql.defaultCacheStorageLevel` = `MEMORY_AND_DISK`, resolved through `StorageLevel.fromString` at [SQLConf.scala:8184](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/internal/SQLConf.scala#L8184). `RDD.cache()` is `MEMORY_ONLY`, so a DataFrame that does not fit **spills** where an RDD would silently recompute

!!! warning "`MEMORY_AND_DISK` means different things in Scala and PySpark"
    The four `StorageLevel` flags are `(useDisk, useMemory, useOffHeap, deserialized)`:

    - **Scala** [`StorageLevel.MEMORY_AND_DISK`](https://github.com/apache/spark/blob/v4.2.0/common/utils/src/main/scala/org/apache/spark/storage/StorageLevel.scala#L157) = `(true, true, false, **true**)` — deserialized
    - **PySpark** [`StorageLevel.MEMORY_AND_DISK`](https://github.com/apache/spark/blob/v4.2.0/python/pyspark/storagelevel.py#L93) = `(True, True, False, **False**)` — **serialized**
    - **PySpark** [`StorageLevel.MEMORY_AND_DISK_DESER`](https://github.com/apache/spark/blob/v4.2.0/python/pyspark/storagelevel.py#L96) = `(True, True, False, True)` — the one matching Scala

    So the level `df.cache()` actually gives you is, in PySpark's vocabulary, `MEMORY_AND_DISK_DESER`. A PySpark user who passes `StorageLevel.MEMORY_AND_DISK` to `persist()` explicitly gets a **different, serialized** level than the default — same name, different behaviour, no warning. Always name the level as PySpark spells it when writing for Python readers.
- [classic/Dataset.scala:1637](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/classic/Dataset.scala#L1637) — `persist(newLevel)`; `storageLevel` (L1643) reports what a DataFrame currently has; `unpersist(blocking)` (L1650)

### The CacheManager — a list of plans, not a property of your variable

- [execution/CacheManager.scala:71](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/CacheManager.scala#L71) — one `CacheManager` per `SharedState`, so **cached data is visible across sessions** on the same context (see B2)
- [execution/CacheManager.scala:99](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/CacheManager.scala#L99) — `cacheQuery`; `cacheQueryInternal` (L133) registers a `CachedData` entry and returns. **Nothing is computed** — `cache()` is a plan annotation, not an action
- [execution/CacheManager.scala:470](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/CacheManager.scala#L470) — `lookupCachedData` (also L478 for a raw plan). Matching is by `sameResult` (L227, L347) — **plan equivalence, not object identity**. Two independently-built but identical plans hit the same cache entry; adding a `filter` to a cached DataFrame misses it entirely and recomputes from source
- [columnar/InMemoryRelation.scala:415](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/columnar/InMemoryRelation.scala#L415) — the plan node substituted on a hit, wrapping a `CachedRDDBuilder`. The columnar batch format and its 4MB/10000-row batching are traced in B3

### `CACHE TABLE` is eager; `df.cache()` is not

- [datasources/v2/CacheTableExec.scala:58](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/v2/CacheTableExec.scala#L58) — `if (!isLazy) df.count()`: the SQL form **materializes immediately**, and un-caches itself if the query fails. `isLazy` (L41) is set by `CACHE LAZY TABLE`. So the two surfaces have opposite defaults, which is invisible from either API alone

### Memory — shared, and the "reservation" is not one

- [memory/UnifiedMemoryManager.scala:58](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/memory/UnifiedMemoryManager.scala#L58) — storage and execution share a single region sized by `spark.memory.fraction` (0.6). `acquireStorageMemory` (L206), `maxOnHeapStorageMemory` (L117)
- `spark.memory.storageFraction` (0.5) is **the floor below which storage cannot be evicted**, not an allocation. Above it, execution wins: a shuffle or aggregation can evict your cached blocks mid-job. This is why caching sometimes appears not to work under memory pressure
- [storage/memory/MemoryStore.scala:309](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/storage/memory/MemoryStore.scala#L309) — `putIteratorAsValues`: unrolls incrementally, reserving *unroll* memory as it goes rather than sizing the block up front. A partition that fails to unroll is dropped instead of caching, which is silent
- [storage/memory/MemoryStore.scala:472](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/storage/memory/MemoryStore.scala#L472) — `evictBlocksToFreeSpace`: LRU eviction. With `MEMORY_ONLY` an evicted block is simply recomputed on next use — correct, and invisible except as unexplained slowness

### Release

- [execution/CacheManager.scala:181](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/CacheManager.scala#L181) — `uncacheQuery`, with cascade semantics for dependent plans
- [ContextCleaner.scala:65](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/ContextCleaner.scala#L65) — GC-driven cleanup: `registerRDDForCleanup` (L153), `doCleanupRDD` (L223). Cached data is released when the object becomes unreachable *and* the cleaner runs (`spark.cleaner.periodicGC.interval`, 30min) — so relying on GC rather than calling `unpersist()` holds memory for a long, unpredictable time

## Chapter notes

**Chapter 17 is a 15-line stub — this trace is source material for writing it, not a gap analysis.** The stub already lists four intended sections (caching as lineage management, storage levels, eviction policy, `unpersist`); the points below are what the source says that a book-derived chapter would likely miss.

### Points the chapter should not miss ❗

- **`df.cache()` defaults to memory-and-disk *deserialized*, while `rdd.cache()` is `MEMORY_ONLY`.** An oversized DataFrame cache spills; an oversized RDD cache silently recomputes. The storage-level section must also carry the naming trap above: in PySpark that default is spelled `MEMORY_AND_DISK_DESER`, and passing `StorageLevel.MEMORY_AND_DISK` explicitly gives a *serialized* level instead. Since this is a PySpark book, use PySpark's names throughout or the chapter will teach the wrong constant.
- **`cache()` computes nothing.** It registers a plan with the `CacheManager` and returns. The data appears on the next action, so the first "cached" read is no faster — the classic benchmarking mistake.
- **`CACHE TABLE` is eager and `df.cache()` is lazy.** Opposite defaults across two surfaces of the same engine, with `CACHE LAZY TABLE` as the opt-out. Neither API hints at this.
- **Cache hits are decided by plan equivalence, not by variable.** `lookupCachedData` matches with `sameResult`. So two separately-built identical plans share one cache entry, while `cached_df.filter(...)` misses and recomputes from source. This is the single most useful thing to know about caching and it is invisible from the API surface.
- **`storageFraction` is an eviction floor, not a reservation.** Execution can evict cached blocks above it mid-job. Explains "I cached it and it still recomputed" without resorting to hand-waving.
- **Eviction of a `MEMORY_ONLY` block is silent.** The block is recomputed on next use — correct results, unexplained slowness. Point the reader at the Storage tab (I7) as the way to see it.
- **The cache manager lives on `SharedState`.** Cached data is visible to other sessions on the same context, and `spark.stop()` discards all of it (connects to B2).
- **Not calling `unpersist()` holds memory until GC plus a 30-minute cleaner interval.** The `ContextCleaner` path makes "it will be collected eventually" much weaker than it sounds.
- **Cached executors are never reclaimed by default under dynamic allocation.** `cachedExecutorIdleTimeout` defaults to effectively infinite, so caching changes cluster scaling behaviour — a cost that does not show up in any query.
- **Checkpointing is the other lineage-truncation tool** and belongs in the comparison: `cache` is a hint that can be evicted, `checkpoint` writes durably and actually truncates lineage (I4).
- **`spark.sql.cache.serializer` is a real extension point.** Worth one line, since it is how Gluten and similar plugins substitute a native cache format.
