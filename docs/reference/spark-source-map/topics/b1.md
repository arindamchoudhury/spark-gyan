## What it is

Spark's execution model separates concerns across four tiers running in a single driver JVM plus one or more executor JVMs. The user-facing entry points are `SparkSession` (SQL/DataFrame API, wraps a `SparkContext`) and `SparkContext` (RDD API, owns all scheduler state). When an action is called, `SparkContext` delegates to `DAGScheduler`, which walks the RDD lineage graph, cuts it at every `ShuffleDependency` boundary to produce a DAG of `Stage` objects, and converts each ready stage into a `TaskSet`. `TaskSchedulerImpl` receives the `TaskSet`, wraps it in a `TaskSetManager` (which tracks per-task retries), and calls `backend.reviveOffers()` on its `SchedulerBackend`. The backend negotiates resources with the cluster manager, then calls `Executor.launchTask()` on each worker, which submits a `TaskRunner` to a thread pool. In local mode the driver, backend, and executor all share one JVM. For PySpark, a Python process communicates with the driver JVM via the Py4J gateway; Python worker processes are spawned per-task for RDD lambdas, but DataFrame operations are fully executed inside the JVM.

Two things sit either side of that core loop and are usually taught as if they were not part of the architecture. **Before** any user code runs, `SparkSubmit` has already decided *which class is actually launched* — in cluster deploy mode your `main()` does not run on the machine you typed the command on, and the driver JVM's heap was fixed before the JVM existed. **Above** the RDD layer, the DataFrame API decides how many jobs an action becomes; "one action, one job" is a useful first approximation and is *false* for `show`, `head` and `take`, which run a partition-scaling loop of jobs.

### How many jobs, how many stages — the DataFrame entry point

The RDD layer answers "what is a job". It cannot answer "how many jobs does `df.show()` submit", because that is decided one layer up, and the answer is not one.

- [Dataset.scala:2320](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/classic/Dataset.scala#L2320) — `withAction`: the single funnel every DataFrame action passes through. It wraps the call in [SQLExecution.withNewExecutionId](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/SQLExecution.scala#L314), which is what groups several Spark *jobs* under one SQL *query* in the UI — the reason the SQL tab and the Jobs tab do not agree on counts
- [Dataset.scala:1461](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/classic/Dataset.scala#L1461) — `head(n)` = `withAction("head", limit(n)…)`. [`getRows`](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/classic/Dataset.scala#L331) calls `take(numRows + 1)`, so `show(10)` is really a `LIMIT 11`
- [SparkPlan.scala:524](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/SparkPlan.scala#L524) — `executeTake`: a **loop**, not a job. It scans `spark.sql.limit.initialNumPartitions` (default **1**) partitions, and if it has not collected `n` rows, multiplies the partition count by `spark.sql.limit.scaleUpFactor` (default **4**) and goes again — calling [`sc.runJob`](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/SparkPlan.scala#L562) once per pass. A selective filter under a `show()` can therefore submit 4–5 jobs over the same query. Both configs are `.internal()`, and their own doc strings say plainly that lower values mean "more jobs will be run"
- [limit.scala:48](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/limit.scala#L48) — `CollectLimitExec`; its `executeCollect` ([L53](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/limit.scala#L53)) delegates straight into that loop
- [SparkStrategies.scala:92](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/SparkStrategies.scala#L92) — `SpecialLimits`, whose [`planTakeOrdered`](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/SparkStrategies.scala#L115) rewrites `Limit(n, Sort(...))` into [`TakeOrderedAndProjectExec`](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/limit.scala#L310) whenever `n < spark.sql.execution.topKSortFallbackThreshold` (default `Integer.MAX_VALUE - 15`, so effectively always). **`orderBy(...).show(10)` performs no global-sort shuffle**: [`executeCollect`](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/limit.scala#L321) takes a per-partition top-*n* and merges on the driver via `RDD.takeOrdered`. Predicting the stage count of a sort-then-show query from the user's chain alone gets it wrong; this rule is why

### Scheduling *within* one application — pools

Concurrent jobs from the same `SparkSession` compete, and the arbitration is a separate mechanism from anything the cluster manager does.

Pools are selected per-thread via the `spark.scheduler.pool` local property
- [SchedulingAlgorithm.scala:29](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/SchedulingAlgorithm.scala#L29) / [:43](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/SchedulingAlgorithm.scala#L43) — the two comparators; `getSortedTaskSetQueue` ([TaskSchedulerImpl.scala:555](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskSchedulerImpl.scala#L555)) applies one of them on **every** resource offer. Under FIFO a long first job starves later ones even with idle cores — the effect usually misread as "the cluster is too small"

### Failure and retry — the paths that decide whether a job survives

- [TaskSetManager.scala:951](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskSetManager.scala#L951) — `handleFailedTask`; aborts the stage once a single task hits `maxTaskFailures` (L1077)
- [TaskSetExcludeList.scala:86](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskSetExcludeList.scala#L86) — `isExecutorExcludedForTask`: repeated failures on one executor exclude it for that task (L102 for the whole task set), so a single bad node does not consume all four attempts
- [TaskSetManager.scala:258](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskSetManager.scala#L258) — `myLocalityLevels` / `localityWaits` (L268): the scheduler waits before demoting locality, which is why tasks can sit idle with free cores available
- [DAGScheduler.scala:2395](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/DAGScheduler.scala#L2395) — `case FetchFailed`: the qualitatively different failure. A fetch failure means an *upstream* stage's output is gone, so the DAGScheduler resubmits the parent stage (`resubmitFailedStages`, L1244) rather than retrying the task. This is the mechanism behind "my job re-ran a stage I thought had finished"
- [DAGScheduler.scala:3079](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/DAGScheduler.scala#L3079) — `handleExecutorLost`: unregisters that executor's map output, which is what turns an executor loss into recomputation
- [TaskSchedulerImpl.scala:113](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskSchedulerImpl.scala#L113) — `speculationScheduler`, started at L233: duplicate attempts for stragglers. Note this interacts with accumulators (see E10) and with any non-idempotent side effect in a task

### Liveness — how an executor is declared dead

The failure paths above all presuppose someone noticed. Two independent timers do that, and both fail *quietly*.

- [Executor.scala:483](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/executor/Executor.scala#L483) — the executor-side `heartbeater`, firing [`reportHeartBeat`](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/executor/Executor.scala#L1519) every `spark.executor.heartbeatInterval` (10s). After `spark.executor.heartbeat.maxFailures` consecutive failures (**60**) the executor [kills itself](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/executor/Executor.scala#L1559) — it exits on its own initiative, so nothing in the driver log explains it
- [HeartbeatReceiver.scala:68](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/HeartbeatReceiver.scala#L68) — the driver-side counterpart; [`executorTimeoutMs`](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/HeartbeatReceiver.scala#L84) comes from `spark.network.timeout` (120s), and [`expireDeadHosts`](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/HeartbeatReceiver.scala#L210) calls `killAndReplaceExecutor` on anything silent for longer. A long full GC is indistinguishable from a dead executor here, which is exactly how a GC problem presents as a mysterious executor loss

### Getting the result back to the driver

- [Executor.scala:1002](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/executor/Executor.scala#L1002) — the executor checks `resultSize` against `maxResultSize` (L420) and **drops the result** rather than sending it — the job then fails with a message about `maxResultSize`, which is why raising the config is sometimes genuinely the fix and sometimes a sign you should not be collecting
- [TaskResultGetter.scala:58](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskResultGetter.scala#L58) — `enqueueSuccessfulTask`; `IndirectTaskResult` (L78) means the result exceeded the RPC frame (`spark.rpc.message.maxSize`, 128 MB) and was put in the block manager for the driver to fetch separately
- [JobWaiter.scala:30](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/JobWaiter.scala#L30) — `taskSucceeded` (L63) accumulates results and completes the future; this is the object that makes `runJob` block

### Observability — and where metrics silently go missing

Everything the UI, the History Server and the event log know arrives as events on one asynchronous bus. It is lossy by design, and that is the one fact worth carrying.

- [LiveListenerBus.scala:46](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/LiveListenerBus.scala#L46) — the bus; [`post`](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/LiveListenerBus.scala#L126) fans each event into four independent queues (`shared`, `executorManagement`, `appStatus`, `eventLog`) so one slow listener cannot block the others
- [AsyncEventQueue.scala:38](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/AsyncEventQueue.scala#L38) — each queue is a bounded `LinkedBlockingQueue` of [`capacity`](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/AsyncEventQueue.scala#L53) = `spark.scheduler.listenerbus.eventqueue.capacity` (10 000). When it is full, events are [**dropped**](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/AsyncEventQueue.scala#L169) and only a rate-limited warning is logged. Nothing fails; the job is unaffected; the UI and the event log simply become wrong. This is the silent-failure path of the whole architecture, and it bites hardest on jobs with very many small tasks
- [EventLoggingListener.scala:48](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/EventLoggingListener.scala#L48) — registered when `spark.eventLog.enabled` is set; writes to `spark.eventLog.dir` for later History Server replay. It is just another listener on that lossy bus

### Elasticity — changing the executor set mid-application

- [ExecutorAllocationManager.scala:102](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/ExecutorAllocationManager.scala#L102) — the driver-side control loop for `spark.dynamicAllocation.enabled`. It reacts to *pending tasks*, not to jobs: a backlog older than [`spark.dynamicAllocation.schedulerBacklogTimeout`](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/ExecutorAllocationManager.scala#L122) (1s) triggers a request, sized by [`maxNumExecutorsNeededPerResourceProfile`](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/ExecutorAllocationManager.scala#L297)
- [CoarseGrainedSchedulerBackend.scala:551](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/cluster/CoarseGrainedSchedulerBackend.scala#L551) — `decommissionExecutors`: the graceful path (spot-instance reclaim, scale-down) that migrates shuffle and cached blocks off an executor before it goes, rather than letting `handleExecutorLost` recompute them

### Barrier execution — the other scheduling model in the same scheduler

- [RDDBarrier.scala:33](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/rdd/RDDBarrier.scala#L33) — `rdd.barrier()` marks a stage gang-scheduled: all tasks start together or none do
- [BarrierTaskContext.scala:171](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/BarrierTaskContext.scala#L171) — `barrier()`: a global sync point *inside* a task, which the ordinary model has no equivalent of
- [DAGScheduler.scala:629](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/DAGScheduler.scala#L629) — `checkBarrierStageWithNumSlots`: fails the job outright ([`BarrierJobSlotsNumberCheckFailed`](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/DAGScheduler.scala#L1424)) when the cluster has fewer slots than the stage has tasks. This is the sharpest illustration that ordinary Spark stages are *elastic* — they simply queue — and that distributed-training workloads are not

### The other architecture: Spark Connect

- [SparkConnectService.scala](https://github.com/apache/spark/blob/v4.2.0/sql/connect/server/src/main/scala/org/apache/spark/sql/connect/service/SparkConnectService.scala) — the gRPC server; the client sends an unresolved plan rather than driving a local `SparkContext`
- [SparkConnectPlanner.scala:90](https://github.com/apache/spark/blob/v4.2.0/sql/connect/server/src/main/scala/org/apache/spark/sql/connect/planner/SparkConnectPlanner.scala#L90) — `SparkConnectPlanner`: converts protobuf relations into Catalyst logical plans server-side. Everything below this point — DAGScheduler, tasks, shuffle — is identical. Worth stating explicitly, because the two-architecture framing suggests more difference than exists: Connect replaces *how the plan arrives*, not how it runs

## Relevant configs

| Config | Default | Effect |
|---|---|---|
| `spark.driver.memory` | 1g | JVM heap for the driver process; read by the launcher, so it must be set before the JVM starts (`spark-submit --driver-memory`) — setting it in application code does nothing |
| `spark.driver.cores` | 1 | Cores allocated to the driver in cluster deploy mode |
| `spark.driver.host` | local canonical hostname | Address advertised to executors for RPC; asserted at `SparkEnv.createDriverEnv`. Override when the driver is behind NAT — executors dial in, so a wrong value hangs rather than errors |
| `spark.driver.maxResultSize` | 1g | Cumulative size limit for task results collected at the driver; oversized results are dropped **at the executor**, not transmitted |
| `spark.executor.memory` | 1g | JVM heap per executor; primary knob for out-of-memory tuning |
| `spark.executor.cores` | 1 | Task slots per executor; higher values share the JVM heap across more concurrent tasks |
| `spark.executor.instances` | (none) | Fixed executor count in static allocation; absent triggers dynamic allocation if enabled |
| `spark.executor.heartbeatInterval` | 10s | How often executors report metrics to the driver; must be less than `spark.network.timeout` |
| `spark.executor.heartbeat.maxFailures` | 60 | Consecutive heartbeat failures after which the **executor exits itself** — a death the driver log does not explain |
| `spark.network.timeout` | 120s | Drives `HeartbeatReceiver`'s executor timeout; a GC pause longer than this is indistinguishable from a dead executor |
| `spark.cores.max` | (none) | Standalone cluster only: max cores the application may claim across all executors |
| `spark.default.parallelism` | backend-dependent | Local: total cores. Cluster: `max(cores registered so far, 2)` — racy at startup, which is why the same code partitions differently on a cluster |
| `spark.task.cpus` | 1 | CPU slots consumed per task; slots per executor are `cores / spark.task.cpus` |
| `spark.task.maxFailures` | 4 | Times a single task may fail before the stage aborts; overridden to 1 in local mode |
| `spark.stage.maxConsecutiveAttempts` | 4 | Stage-level retries after fetch failures, distinct from task retries |
| `spark.locality.wait` | 3s | How long the scheduler holds out for a better locality level — the reason cores can sit idle with tasks pending |
| `spark.speculation` | false | Launch duplicate attempts for straggler tasks |
| `spark.scheduler.mode` | FIFO | `FIFO` or `FAIR`; applied by `getSortedTaskSetQueue` on every resource offer. Under FIFO a long first job starves later ones even with free cores |
| `spark.scheduler.allocation.file` | (none) | FAIR-mode pool definitions; falls back to `fairscheduler.xml` on the classpath |
| `spark.scheduler.minRegisteredResourcesRatio` | (none) | Fraction of expected executors to wait for before scheduling starts |
| `spark.scheduler.maxRegisteredResourcesWaitingTime` | 30s | Hard cap on that wait — after it, the first stage runs at whatever parallelism has registered |
| `spark.scheduler.listenerbus.eventqueue.capacity` | 10000 | Per-queue bound on the listener bus; overflow **silently drops events**, corrupting the UI, metrics and event log without failing the job |
| `spark.submit.deployMode` | client | `client` (driver in submitting process) vs `cluster` (a launcher class runs instead, and your `main()` executes elsewhere) |
| `spark.dynamicAllocation.enabled` | false | Driver-side `ExecutorAllocationManager` adds/removes executors from pending-task backlog |
| `spark.dynamicAllocation.schedulerBacklogTimeout` | 1s | Backlog age that triggers a request for more executors |
| `spark.storage.decommission.enabled` | false | Migrate shuffle/cached blocks off an executor being decommissioned instead of recomputing them |
| `spark.shuffle.sort.bypassMergeThreshold` | 200 | Partition count at or below which `BypassMergeSortShuffleWriter` is chosen — crossing it silently changes the shuffle writer |
| `spark.rpc.message.maxSize` | 128 (MB) | Above this a task result becomes an `IndirectTaskResult` fetched from the block manager |
| `spark.eventLog.enabled` | false | When true, writes `SparkListenerEvent`s for post-mortem replay in the History Server |
| `spark.eventLog.dir` | /tmp/spark-events | Destination for event log files (local or HDFS) |
| `spark.sql.limit.initialNumPartitions` | 1 | *(internal)* Partitions scanned on the first pass of `executeTake`; low values mean more jobs per action |
| `spark.sql.limit.scaleUpFactor` | 4 | *(internal)* Multiplier per subsequent pass — so one `show()` can be several jobs |
| `spark.sql.execution.topKSortFallbackThreshold` | 2147483632 | Below this limit, `Sort + Limit` becomes `TakeOrderedAndProjectExec` and the global-sort shuffle disappears |
