## What it is

Spark's execution model separates concerns across four tiers running in a single driver JVM plus one or more executor JVMs. The user-facing entry points are `SparkSession` (SQL/DataFrame API, wraps a `SparkContext`) and `SparkContext` (RDD API, owns all scheduler state). When an action is called, `SparkContext` delegates to `DAGScheduler`, which walks the RDD lineage graph, cuts it at every `ShuffleDependency` boundary to produce a DAG of `Stage` objects, and converts each ready stage into a `TaskSet`. `TaskSchedulerImpl` receives the `TaskSet`, wraps it in a `TaskSetManager` (which tracks per-task retries), and calls `backend.reviveOffers()` on its `SchedulerBackend`. The backend negotiates resources with the cluster manager, then calls `Executor.launchTask()` on each worker, which submits a `TaskRunner` to a thread pool. In local mode the driver, backend, and executor all share one JVM. For PySpark, a Python process communicates with the driver JVM via the Py4J gateway; Python worker processes are spawned per-task for RDD lambdas, but DataFrame operations are fully executed inside the JVM.

### What a task actually does (shuffle write, the stage boundary in practice)

- [ShuffleMapTask.scala:54](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/ShuffleMapTask.scala#L54) — `ShuffleMapTask`; `runTask` (L82) returns a `MapStatus`, not data. The stage boundary *is* this return type: a shuffle-map stage produces file locations, a result stage produces values ([ResultTask.scala:78](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/ResultTask.scala#L78))
- [SortShuffleManager.scala:145](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/shuffle/sort/SortShuffleManager.scala#L145) — `getWriter` picks one of **three** writers, and which one you get is a performance cliff most tuning advice never names:
  - [BypassMergeSortShuffleWriter.java:84](https://github.com/apache/spark/blob/v4.2.0/core/src/main/java/org/apache/spark/shuffle/sort/BypassMergeSortShuffleWriter.java#L84) — no sort, one file per reduce partition; gated by `shouldBypassMergeSort` ([SortShuffleWriter.scala:118](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/shuffle/sort/SortShuffleWriter.scala#L118)), which requires no map-side combine and partitions ≤ `spark.shuffle.sort.bypassMergeThreshold`
  - [UnsafeShuffleWriter.java:70](https://github.com/apache/spark/blob/v4.2.0/core/src/main/java/org/apache/spark/shuffle/sort/UnsafeShuffleWriter.java#L70) — serialized (Tungsten) shuffle, sorts pointers not objects; gated by `canUseSerializedShuffle` ([SortShuffleManager.scala:227](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/shuffle/sort/SortShuffleManager.scala#L227))
  - [SortShuffleWriter.scala:29](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/shuffle/sort/SortShuffleWriter.scala#L29) — the general fallback
- [MapOutputTracker.scala:594](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/MapOutputTracker.scala#L594) — `getMapSizesByExecutorId`: how a reduce task learns where its inputs live. The driver-side registry (`MapOutputTrackerMasterEndpoint`, L516) is the reason a lost executor invalidates map output
- [BlockStoreShuffleReader.scala:33](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/shuffle/BlockStoreShuffleReader.scala#L33) — the read side; `read()` at L72
- [ShuffleBlockFetcherIterator.scala:86](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/storage/ShuffleBlockFetcherIterator.scala#L86) — fetches remote blocks with a memory budget; where a `FetchFailedException` originates

### Failure and retry — the paths that decide whether a job survives

- [TaskSetManager.scala:951](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskSetManager.scala#L951) — `handleFailedTask`; aborts the stage once a single task hits `maxTaskFailures` (L1077)
- [TaskSetExcludeList.scala:86](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskSetExcludeList.scala#L86) — `isExecutorExcludedForTask`: repeated failures on one executor exclude it for that task (L102 for the whole task set), so a single bad node does not consume all four attempts
- [TaskSetManager.scala:258](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskSetManager.scala#L258) — `myLocalityLevels` / `localityWaits` (L268): the scheduler waits before demoting locality, which is why tasks can sit idle with free cores available
- [DAGScheduler.scala:2395](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/DAGScheduler.scala#L2395) — `case FetchFailed`: the qualitatively different failure. A fetch failure means an *upstream* stage's output is gone, so the DAGScheduler resubmits the parent stage (`resubmitFailedStages`, L1244) rather than retrying the task. This is the mechanism behind "my job re-ran a stage I thought had finished"
- [DAGScheduler.scala:3079](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/DAGScheduler.scala#L3079) — `handleExecutorLost`: unregisters that executor's map output, which is what turns an executor loss into recomputation
- [TaskSchedulerImpl.scala:113](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskSchedulerImpl.scala#L113) — `speculationScheduler`, started at L233: duplicate attempts for stragglers. Note this interacts with accumulators (see E10) and with any non-idempotent side effect in a task

### Getting the result back to the driver

- [Executor.scala:1002](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/executor/Executor.scala#L1002) — the executor checks `resultSize` against `maxResultSize` (L420) and **drops the result** rather than sending it — the job then fails with a message about `maxResultSize`, which is why raising the config is sometimes genuinely the fix and sometimes a sign you should not be collecting
- [TaskResultGetter.scala:58](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/TaskResultGetter.scala#L58) — `enqueueSuccessfulTask`; `IndirectTaskResult` (L78) means the result exceeded the RPC frame and was put in the block manager for the driver to fetch separately
- [JobWaiter.scala:30](https://github.com/apache/spark/blob/v4.2.0/core/src/main/scala/org/apache/spark/scheduler/JobWaiter.scala#L30) — `taskSucceeded` (L63) accumulates results and completes the future; this is the object that makes `runJob` block

### The other architecture: Spark Connect

- [SparkConnectService.scala](https://github.com/apache/spark/blob/v4.2.0/sql/connect/server/src/main/scala/org/apache/spark/sql/connect/service/SparkConnectService.scala) — the gRPC server; the client sends an unresolved plan rather than driving a local `SparkContext`
- [SparkConnectPlanner.scala:90](https://github.com/apache/spark/blob/v4.2.0/sql/connect/server/src/main/scala/org/apache/spark/sql/connect/planner/SparkConnectPlanner.scala#L90) — `SparkConnectPlanner`: converts protobuf relations into Catalyst logical plans server-side. Everything below this point — DAGScheduler, tasks, shuffle — is identical. Worth stating explicitly, because the two-architecture framing suggests more difference than exists: Connect replaces *how the plan arrives*, not how it runs

### Not in spark-book — needs addition ❌

The 2026-06-06 pass closed every gap against Spark 4.1.2. Re-tracing against 4.2.0 opens three new ones, all in Ch03:

- **Ch03 states Java 17/21 only — now false.** The chapter says "Spark 4.x supports only these two LTS releases." Spark 4.2.0 builds and runs on **Java 25** ([SPARK-51167]). This is a factual error, not an omission, and is why Ch03 and topic B1 both carry 🔄.
- **Scala 2.13 is the only option on Spark 4.x.** Ch03 does not state this. Worth one line, because it decides which artifact suffix every dependency needs (`_2.13`) and silently breaks builds copied from Spark 3.x material.
- **Pinned version drift.** Ch03's header still reads `Spark 4.1.x`; the install commands and the `pip install pyspark` bundle discussion are still correct, but the version line needs bumping when the Java claim is fixed.

The completeness pass then opened five more, all in Ch02 — which the earlier trace had marked clean because it only checked the layers that trace had covered:

- **The three shuffle writers.** Ch02 explains stage boundaries and shuffle conceptually but never mentions that `getWriter` picks between `BypassMergeSortShuffleWriter`, `UnsafeShuffleWriter` and `SortShuffleWriter`, or what gates each. This is a real performance cliff — crossing `spark.shuffle.sort.bypassMergeThreshold`, or introducing a map-side combine, silently changes which writer runs.
- **`FetchFailed` is not an ordinary task failure.** Ch02 covers `spark.task.maxFailures` and task retry, but a fetch failure resubmits the *parent stage* instead of retrying the task, because the upstream output is gone. This is the mechanism behind "a stage I thought had completed ran again", and nothing in the chapter explains it.
- **Executor loss causes recomputation via `MapOutputTracker`.** The chapter mentions fault tolerance through lineage; the concrete mechanism — losing an executor unregisters its map output, forcing upstream recomputation — is absent.
- **`maxResultSize` drops results at the executor.** The executor discards an oversized result rather than transmitting it. Worth naming in a chapter that discusses the driver/executor boundary, since it is a common first encounter with that boundary being real.
- **Locality wait.** `myLocalityLevels` / `localityWaits` explain the counterintuitive observation of idle cores while tasks wait — the scheduler is holding out for a better locality level.

Ch02's existing architecture, scheduler, and Py4J material re-verified cleanly against 4.2.0, including the `sql.classic` split and local-mode `maxTaskFailures = 1`.
