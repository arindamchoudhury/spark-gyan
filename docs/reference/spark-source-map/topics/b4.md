## What it is

Reading and writing are two symmetric builder APIs over a common resolution layer. `spark.read` returns a `DataFrameReader` that accumulates a format, a schema, and an option map, then calls `load()`; `df.write` returns a `DataFrameWriter` that accumulates a format, a `SaveMode`, partitioning columns and options, then calls `save()`. Both funnel into `DataSource`, which resolves the format string to a provider class, infers or accepts a schema, and produces either a relation to scan or a write plan to execute.

The part that surprises people is that neither reading nor writing is one operation. A read is *provider lookup → schema resolution (inference or declaration) → partition discovery → file splitting into tasks*, and only the last step is parallel. A write is *plan → commit protocol → per-task file writes → commit*, where the atomicity you get depends entirely on the commit protocol, not on Spark.

## Chapter notes

Gap analysis against **spark-book Ch 07** (`spark-book/ch07-reading-writing-data.md`, 186 lines).

### Already in spark-book ✅

- `spark.read` / `df.write` builder shape, `format`/`option`/`load`/`save`
- CSV read options worked through in a build-up section
- Schema declaration with `StructType` vs `inferSchema`, and the cost of inference
- The four save modes and their semantics
- `partitionBy` on writes and the resulting directory layout
- The `partitionOverwriteMode=dynamic` pitfall — that a partitioned `overwrite` otherwise replaces the whole table (Common pitfalls, line 147)
- Why Parquet is preferred for analytical workloads

### Not in spark-book — needs addition ❌

- **`insertInto` is position-based; `saveAsTable` is name-based.** `insertInto` (`DataFrameWriter:315`) matches columns by *ordinal*, ignoring names entirely — so a DataFrame with correct column names in the wrong order writes silently corrupted data. `saveAsTable` (L444) resolves by name. This is the highest-consequence distinction in the writer API and the chapter covers neither method.
- **The read-parallelism formula.** `maxSplitBytes = min(maxPartitionBytes, max(openCostInBytes, totalBytes / cores))` (`FilePartition:119`) is what actually determines how many tasks a read produces. The chapter never mentions `maxPartitionBytes` or `openCostInBytes`, which leaves "why did my read only get 2 tasks" unanswerable. It also explains the small-files problem concretely: each file costs at least `openCostInBytes` (4 MB) of notional budget regardless of its real size.
- **`maxRecordsPerFile` as the output-file-size control.** The chapter discusses `partitionBy` but not row-capping, which is the direct lever for "my write produced one 8 GB file".
- **Schema inference reads the data twice.** `getOrInferFileFormatSchema` (`DataSource:180`) runs a full inference pass before the real read when no schema is supplied. The chapter says inference is costly; it does not say *why*, and the mechanism is what makes the argument stick.
- **ORC defaults to `zstd` while Parquet defaults to `snappy`.** An easy inconsistency to trip over when comparing formats or matching an existing dataset's codec.
- **`ignoreCorruptFiles` / `ignoreMissingFiles`.** Both default `false`. `ignoreMissingFiles` matters specifically when reading a path another job is concurrently rewriting — a common lakehouse failure the chapter does not cover.
- **`jsonGenerator.ignoreNullFields` defaults to `true`.** Writing JSON silently drops null-valued keys, so a read-write-read round trip does not preserve the schema. Worth one line in a chapter that covers JSON.
- **Reading JSON from an `RDD[String]` / `Dataset[String]`** (`DataFrameReader:158`, L163) — the route for JSON already in memory or arriving from Kafka, rather than from a path.

- **`DROPMALFORMED` silently discards rows.** `FailureSafeParser` (L70) returns `Iterator.empty` for a bad record — no count, no log, no corrupt-record column. The chapter covers reader options but not the parse modes, and this is the one that loses data without telling you. `PERMISSIVE` (the default) is safer only if you actually select `columnNameOfCorruptRecord`; otherwise the malformed rows arrive as all-null and look like ordinary missing data.

- **Predicate pushdown is best-effort, not guaranteed.** `ParquetFilters.createFilter` returns an `Option`, and filters it cannot convert are dropped and re-evaluated in Spark (`ParquetFileFormat:247`, comment at L258). The chapter presents pushdown as a property of Parquet; it is a property of *this filter on this type*, which is why an unexpected full scan is often a type problem rather than a format problem.

- **File listing happens on the driver first.** `bulkListLeafFiles` (`InMemoryFileIndex:149`) lists serially on the driver until the path count exceeds `parallelPartitionDiscoveryThreshold`. This is the answer to "my job sat idle for two minutes before any task started" on a many-partition table — a symptom the chapter cannot currently explain.

- **The commit protocol is where write atomicity comes from — and it is not atomic on object stores.** `HadoopMapReduceCommitProtocol` writes into `_temporary` and *moves* files on `commitJob`. On HDFS a rename is atomic and cheap; on S3 it is a copy, which is both slow and non-atomic. This is the single most important thing to understand about writing to a cloud lakehouse, it is the reason Delta and Iceberg exist, and the chapter does not mention commit at all.

- **`PartitionedFile` is a slice, not a file.** A task reads a `Seq[PartitionedFile]`, each a `(path, offset, length)` range (`FileScanRDD:57`). "One task per file" is wrong in both directions: splittable formats give several tasks per large file, and many small files are packed into one task.

- **`DataFrameWriterV2` exists and replaces `SaveMode` with named operations** — `append()`, `overwrite(condition)`, `createOrReplace()` (`DataFrameWriterV2:188–206`). The chapter teaches only the V1 `mode(...)` string API. Worth at least a forward reference, since the V2 API is where the ecosystem is heading.

- **`bucketBy` only applies to table writes.** `bucketBy` on a plain `save(path)` is silently ineffective; the `bucketSpec` is only honoured on the `saveAsTable` path (`DataFrameWriter:95`, threaded at L575).
