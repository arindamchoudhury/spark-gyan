## What it is

B4 traced *how* Spark reads and writes files — the builders, `DataSource` resolution, splitting, and the commit protocol. This topic is about **what the files themselves are**, and the one distinction that drives every other difference: whether a format stores values **by row** or **by column**.

Columnar formats (Parquet, ORC) store each column's values contiguously with statistics per chunk. That single fact gives column pruning, predicate pushdown, better compression from type-homogeneous runs, and — the part usually left out — a *different execution path* in Spark: a vectorized reader that fills `ColumnarBatch`es directly, bypassing per-row object construction until something forces a conversion.

Row formats (Avro, JSON, CSV) store complete records together. That makes them good at whole-row reads, appends and schema evolution, and bad at analytical scans. Delta and Iceberg are not a third category — they are **metadata layers over Parquet** (I8, I11).

### The vectorized path — why columnar is fast in Spark specifically

- [parquet/VectorizedParquetRecordReader.java:67](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/java/org/apache/spark/sql/execution/datasources/parquet/VectorizedParquetRecordReader.java#L67) — reads a **row group at a time into column vectors**; `nextBatch()` (L238, L241) is the loop. No `InternalRow` is constructed while this path runs
- [vectorized/OnHeapColumnVector.java:32](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/java/org/apache/spark/sql/execution/vectorized/OnHeapColumnVector.java#L32) and [OffHeapColumnVector.java:32](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/java/org/apache/spark/sql/execution/vectorized/OffHeapColumnVector.java#L32) — one array per column, selected by `spark.sql.columnVector.offheap.enabled`
- [vectorized/ColumnarBatch.java:30](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/java/org/apache/spark/sql/vectorized/ColumnarBatch.java#L30) — a batch of column vectors, 4096 rows by default
- [execution/Columnar.scala:67](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/Columnar.scala#L67) — `ColumnarToRowExec`: **the boundary**. Columnar execution in open-source Spark is essentially *scan-only* — the batch is converted to rows as soon as an operator cannot consume it, which for most plans is immediately. Seeing this node high in a plan means the columnar advantage ended at the scan

  This is the honest version of "Spark is columnar": the *reader* is vectorized, the *engine* is row-based (Tungsten `UnsafeRow`), and `ColumnarToRowExec` is where one becomes the other. Plugins like Gluten exist to push the columnar boundary further up

### Pushdown and schema translation

- [parquet/ParquetFilters.scala:50](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/parquet/ParquetFilters.scala#L50) — `createFilter` (L638, helper L697) returns an `Option`, so a predicate it cannot translate is **silently dropped** and re-evaluated in Spark (B4). Pushdown is per-filter and best-effort, not a property of the format
- [parquet/ParquetSchemaConverter.scala:57](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/parquet/ParquetSchemaConverter.scala#L57) — Parquet → Spark types; [L599](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/parquet/ParquetSchemaConverter.scala#L599) — Spark → Parquet. Neither type system is a superset of the other, which is where `binaryAsString`, `nanosAsLong` and the field-ID options come from

### ORC — same architecture, different defaults

- [orc/OrcFileFormat.scala:49](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/orc/OrcFileFormat.scala#L49) and [orc/OrcColumnarBatchReader.java:48](https://github.com/apache/spark/blob/v4.2.0/sql/core/src/main/java/org/apache/spark/sql/execution/datasources/orc/OrcColumnarBatchReader.java#L48) — the same vectorized shape as Parquet. The defaults differ, though: ORC compresses with **zstd**, Parquet with **snappy**

### Avro — row-oriented, and not built in

- [sql/api/.../VariantType.scala:30](https://github.com/apache/spark/blob/v4.2.0/sql/api/src/main/scala/org/apache/spark/sql/types/VariantType.scala#L30) and [VariantVal.java:48](https://github.com/apache/spark/blob/v4.2.0/common/unsafe/src/main/java/org/apache/spark/unsafe/types/VariantVal.java#L48) — `VARIANT` (Spark 4.0): binary-encoded semi-structured data queryable without a declared schema, now with a native Parquet representation. ## Chapter notes

**Chapter 21 is not yet written — this trace is drafting material.** The topic scopes it as: columnar vs row storage, predicate pushdown, column pruning, Parquet row groups and footers, and when to use each format. Note B4 already covers the reader/writer mechanics, so this chapter should stay on the formats themselves.

### Points the chapter should not miss ❗

- **"Spark is columnar" is only true at the scan.** The vectorized reader fills `ColumnarBatch`es, but `ColumnarToRowExec` converts them to `UnsafeRow` as soon as an operator cannot consume columnar input — which for most plans is immediately. The engine is row-based; the *reader* is vectorized. Stating this honestly explains both why Parquet is fast and why the gain is bounded, and it is what makes plugins like Gluten comprehensible.
- **Pushdown is per-filter and best-effort.** `ParquetFilters.createFilter` returns an `Option`; unconvertible predicates are dropped and re-evaluated. So an unexpected full scan is often a *type* problem, not a format problem (B4).
- **ORC and Parquet are the same architecture with different defaults.** Same vectorized reader shape, but ORC writes zstd and Parquet writes snappy. Worth a direct comparison rather than treating them as unrelated.
- **Avro is a separate artifact, not built in.** It lives under `connector/`, is discovered via `DataSourceRegister`, and has no vectorized reader because there is nothing columnar to vectorize. That is the concrete version of "row format".
- **`from_avro`/`to_avro` are a different use case from reading `.avro` files** — decoding Avro bytes inside a column, which is the Kafka pattern (A12).
- **Delta and Iceberg are not formats in this list.** Both are metadata layers over Parquet. A chapter comparing "Parquet, Delta, Avro, JSON" as peers teaches a category error; the right framing is storage format versus table format (I8, I11).
- **`VARIANT` changes the JSON conversation.** Semi-structured data no longer means "parse a string column or declare a rigid schema" — there is a queryable binary type with a native Parquet representation (I1). The books predate it.
- **Field-ID matching exists in Parquet too.** `spark.sql.parquet.fieldId.read.enabled` is the same discipline Iceberg applies by default (I11), and it is what makes renames safe.
- **Datetime rebase modes are a real correctness setting.** Dates before 1582 written by older Spark need explicit handling; `CORRECTED` is the current default and silently differs from legacy behaviour.
