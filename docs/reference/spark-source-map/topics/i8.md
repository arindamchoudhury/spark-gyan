## What it is

Delta Lake is not a storage format Spark knows about. It is a **plugin**: a jar that registers itself through `spark.sql.extensions` and a catalog implementation, and thereafter intercepts planning for tables whose directory contains a `_delta_log`. Everything else — the DataFrame API, the scheduler, the shuffle — is unchanged.

The table itself is a directory of Parquet data files plus that `_delta_log` directory of ordered JSON commits. A *snapshot* is the result of replaying those commits: the set of `AddFile` entries not subsequently removed. Reading a Delta table means computing a snapshot and then scanning the files it names; writing means computing what changed and attempting to append the next numbered commit file, which succeeds only if no one else took that number first.

That last sentence is the whole of Delta's ACID story: **atomicity comes from a single filesystem operation — creating file `N.json` — not from a database.**

## Key source locations

Delta anchors verified against the `v4.3.1` tag of `delta-io/delta` on 2026-07-18. Spark-side anchors are `v4.2.0` as elsewhere.

### Registration — Delta is a plugin, not a built-in

- [DeltaSparkSessionExtension.scala:72](https://github.com/delta-io/delta/blob/v4.3.1/spark-unified/src/main/scala/io/delta/sql/DeltaSparkSessionExtension.scala#L72) — the class named by `spark.sql.extensions`. It injects resolution rules (L83, L90, L95) into the analyzer, which is how Delta-specific SQL and table resolution reach Catalyst. This is the concrete payoff of B2's finding that `spark.sql.extensions` is a **static** config: set it after the session exists and Delta simply is not installed
- [sources/DeltaDataSource.scala:55](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/sources/DeltaDataSource.scala#L55) — the `"delta"` short name, resolved through the same `DataSourceRegister`/`ServiceLoader` mechanism as every built-in format (B4)

### The log and the snapshot

- [DeltaLog.scala:80](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/DeltaLog.scala#L80) — one `DeltaLog` per table path, cached; the object that owns log access
- [SnapshotManagement.scala:478](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/SnapshotManagement.scala#L478) — `getLogSegmentForVersion`: assembles the newest checkpoint plus the JSON commits after it. Reading a table starts by **listing the log directory**, which is why `_delta_log` size affects query start-up
- [Snapshot.scala:106](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/Snapshot.scala#L106) — the reconstructed table state; `stateDS` (L385) and `allFiles` (L396). **State reconstruction is itself a Spark job**: the file list is computed as a `Dataset`, so the "which files do I read" step is distributed work, not a directory listing

### The actions — a Delta table's entire semantics in five case classes

- [actions.scala:899](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/actions/actions.scala#L899) — `AddFile`: path, partition values, size, and **statistics**. Those stats are what enable data skipping, and they are why a Delta scan can prune files without opening them
- [actions.scala:1143](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/actions/actions.scala#L1143) — `RemoveFile`: a **tombstone**. A delete does not remove data; it appends a record saying the file is no longer current. This is why time travel works and why `VACUUM` is a separate operation
- [actions.scala:1235](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/actions/actions.scala#L1235) — `Metadata`: schema, partitioning, properties. Schema lives *in the log*, not in a metastore — which is why a Delta table is self-describing and portable
- [actions.scala:231](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/actions/actions.scala#L231) — `Protocol`: minimum reader/writer versions. An older client refuses a table using newer features rather than corrupting it
- [actions.scala:1385](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/actions/actions.scala#L1385) — `CommitInfo`: the provenance row `DESCRIBE HISTORY` renders

### Writes — optimistic concurrency

- [OptimisticTransaction.scala:182](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/OptimisticTransaction.scala#L182) — a transaction reads a snapshot, tracks what it depended on, and only at `commit` (L1626/L1643) attempts to write
- [OptimisticTransaction.scala:2619](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/OptimisticTransaction.scala#L2619) — `doCommitRetryIteratively`: the retry loop. Writing commit *N+1* succeeds only if that filename does not yet exist
- [ConflictChecker.scala:217](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/ConflictChecker.scala#L217) — when someone else won the race, Delta does **not** simply fail. `checkConflictsAndValidateActions` (L239) and `checkConflicts` (L274) test whether the two transactions are logically compatible — two appends usually are — and retry against the newer snapshot. Only a genuine conflict raises `DeltaConcurrentModificationException` ([OptimisticTransaction.scala:1863](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/OptimisticTransaction.scala#L1863))

### Compaction, retention, time travel

- [Checkpoints.scala:253](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/Checkpoints.scala#L253) — checkpoints collapse the JSON history into Parquet so replay does not grow without bound; written every `CHECKPOINT_INTERVAL` commits (L267), default 10
- [commands/VacuumCommand.scala:60](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/commands/VacuumCommand.scala#L60) — deletes files that are both unreferenced *and* older than the retention window. **`VACUUM` is what destroys time travel**, and the retention check exists to stop you doing it accidentally
- [DeltaTimeTravelSpec.scala:39](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/DeltaTimeTravelSpec.scala#L39) — `VERSION AS OF` / `TIMESTAMP AS OF`: selecting an older snapshot, which works only while the files it references still exist

| `spark.databricks.delta.stalenessLimit` | `0` | Permitted snapshot staleness before a refresh |

## Chapter notes

**Chapter 19 is not yet written — this trace is drafting material.** The learning-path topic scopes it as: writing and reading Delta tables, ACID transactions, the transaction log, `DESCRIBE HISTORY`, time travel, `VACUUM`, `OPTIMIZE`.

### Points the chapter should not miss ❗

- **Delta is a plugin that installs through `spark.sql.extensions`, and that config is static.** The single most common setup failure — "my Delta SQL isn't recognised" — is this config being set after the session exists. Direct payoff of the B2 finding, and it belongs at the front of the chapter rather than in a troubleshooting note.
- **Atomicity is one filesystem operation: creating `N.json`.** No lock service, no coordinator. Two writers race to create the same numbered file and exactly one wins. Saying this plainly makes the whole ACID story concrete, and it explains why Delta's guarantees depend on the storage system's rename/put semantics — which is the loop back to B4's finding about non-atomic commits on object stores.
- **A conflict is not automatically a failure.** The `ConflictChecker` tests whether two transactions are *logically* compatible and retries against the newer snapshot — two concurrent appends normally both succeed. Only real conflicts raise. Chapters usually present concurrency as "one wins, one fails", which is more pessimistic than the implementation.
- **A delete writes a tombstone; it does not delete.** `RemoveFile` is an append. Time travel is not a special feature bolted on — it is the natural consequence of never removing anything. And `VACUUM` is the operation that trades it away.
- **State reconstruction is a Spark job.** `allFiles` is a `Dataset`, so working out which files to read is distributed work over the log. This explains why many small commits slow down *query planning*, and why checkpoints matter.
- **Statistics live in `AddFile`.** Data skipping comes from per-file stats in the log, not from the Parquet footers — a different mechanism from B4's Parquet pushdown, and worth distinguishing since both are called "skipping".
- **Schema lives in the log, not a metastore.** `Metadata` makes a Delta table self-describing, which is why a path-based table needs no catalog at all.
- **`Protocol` versions cause refusal, not corruption.** An older reader declines a table using newer features. Reassuring, and the reason version upgrades are one-way.
- **`DESCRIBE HISTORY` is reading `CommitInfo` actions** — provenance is stored in the log like everything else, not in a side table.
