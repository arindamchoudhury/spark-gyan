# Python↔JVM Boundary and UDF Cost

> *Cross-chapter synthesis — Rioux (2022), Chapters 1, 8.*
>
> Every PySpark program runs on two runtimes: the JVM (where Spark executes) and Python (where your code lives). The boundary between them is where serialisation happens — and serialisation cost is what makes Python UDFs expensive and why the DataFrame API is fast.

---

## Ch 1 — The DataFrame API erases the language gap

The PySpark DataFrame API is a thin Python wrapper over the Spark JVM engine. When you call `df.filter(F.col("x") > 0)`, Python builds a *description* of the operation (a logical plan node) and passes it to the JVM. The JVM compiles and executes it. Python is not involved during execution.

This means a DataFrame job written in Python runs at the same speed as one written in Scala or Java — all languages produce the same Catalyst plan and the same Tungsten bytecode.

The language gap only reappears at the **Python↔JVM boundary** — whenever Python code must actually *run* during execution (UDFs, RDD lambdas).

---

## Ch 8 — Where the boundary is crossed

**Actions that cross the boundary:**

| Crossing point | Direction | Notes |
|---|---|---|
| `df.collect()` | JVM → Python | All rows serialised and sent to the driver |
| `df.toPandas()` | JVM → Python | Uses Arrow by default in Spark 3.3+ |
| `df.show()` | JVM → Python (driver only) | Only the displayed rows |
| Python UDF called in a transformation | JVM → Python (executor) → JVM | Per-row or per-batch, every executor |
| RDD `map(lambda)`, `filter(lambda)`, etc. | JVM → Python (executor) → JVM | Per-partition, every operation |
| RDD `collect()` | JVM → Python (driver) | All partitions |

The executor-side crossings (UDFs, RDD lambdas) are the expensive ones — they happen at scale, on every partition, for every operation in the chain.

## Ch 8 — UDF evaluation types

When you register a UDF, Spark chooses an evaluation strategy based on how it was created:

| UDF type | How created | Serialisation | Performance |
|---|---|---|---|
| `SQL_BATCHED_UDF` | `@F.udf` / `F.udf()` with standard Python function | Row-by-row pickle | Slowest |
| `SQL_ARROW_BATCHED_UDF` | `@F.udf` with `useArrow=True`, or pandas UDF `@F.pandas_udf` with scalar type | Arrow batch per partition | ~10× faster than row-by-row |
| `SQL_TABLE_UDF` | `@F.pandas_udf` with iterator or grouped map type | Arrow batches, streaming | Flexible for stateful per-group logic |

**Suppressing the Spark 4.x Arrow inference warning.**

In Spark 4.x, `@F.udf` on a function with type annotations tries to infer Arrow batching automatically. If you want standard row-by-row evaluation, suppress the inference warning explicitly:

```python
@F.udf(returnType=T.StringType(), useArrow=False)
def my_udf(value: str) -> str:
    return value.upper()
```

## Ch 8 — The cloudpickle bridge for RDD operations

Classic RDD operations use **cloudpickle** to serialise the Python function (lambda or named function) and send it to each executor. Cloudpickle captures closures, so the function and any objects it closes over are all serialised.

The cost model:

```
For each RDD operation (e.g., .map(f)):
  For each partition (e.g., 200 partitions):
    1. Serialise partition data (pickle) — JVM → Python socket
    2. Start Python worker (or reuse from pool)
    3. Deserialise partition data in Python worker
    4. Apply f() to each element
    5. Serialise results (pickle) — Python → JVM socket
    6. Deserialise results on JVM side
```

Five chained RDD operations × 200 partitions = 1,000 serialise/deserialise cycles.

**Minimising boundary crossings:**

```python
# Bad: two separate map operations → two boundary crossings per partition
rdd.map(lambda x: x.strip()).map(lambda x: x.upper()).collect()

# Good: one map with composed logic → one crossing per partition
rdd.map(lambda x: x.strip().upper()).collect()
```

## Ch 8 — UDFs and whole-stage code generation

Python UDFs interrupt Catalyst's **whole-stage code generation (WSCG)**. WSCG fuses consecutive DataFrame operations into a single compiled JVM bytecode class. A UDF is a black box to Catalyst — it cannot be fused into the bytecode. Spark must:

1. Materialise the row at the UDF boundary (exit the fused loop).
2. Serialise and call the Python UDF.
3. Deserialise the result and re-enter the fused loop.

Every UDF in a pipeline creates a WSCG barrier. Three consecutive UDFs = three barriers, three serialise/deserialise cycles per row.

**The rule:** reach for a built-in `pyspark.sql.functions` implementation before writing a UDF. Built-ins compile into the generated bytecode; UDFs do not.

```python
# Fast: built-in, compiles into WSCG bytecode
df.withColumn("upper", F.upper(F.col("name")))

# Slow: Python UDF, breaks WSCG, serialises every row
@F.udf(returnType=T.StringType())
def slow_upper(s):
    return s.upper() if s else None

df.withColumn("upper", slow_upper(F.col("name")))
```

---

## Summary

- The DataFrame API builds a logical plan in Python and hands it to the JVM — no Python↔JVM crossing during execution.
- Python UDFs cross the JVM boundary per-row (standard) or per-Arrow-batch (pandas UDF); each crossing has serialisation cost.
- Classic RDD lambdas cross the boundary per-partition, per-operation (cloudpickle).
- Compose RDD lambdas to minimise boundary crossings.
- UDFs are WSCG barriers — prefer built-in `F.*` functions, which compile into generated bytecode.
- Arrow-batched UDFs (`useArrow=True` / `@F.pandas_udf`) cut serialisation cost by ~10× vs row-by-row.
